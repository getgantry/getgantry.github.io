Gantry/Kubernetes auf apple/container

Kubernetes auf Apple container

apple/container kann einen Kubernetes-Cluster ausführen, dessen Nodes Container auf deinem Mac sind. Gantry ist die GUI dafür: Erstelle einen Cluster, sieh zu, wie seine Nodes starten, führe deine lokalen Images darin aus und durchsuche Pods, Logs und Services, ohne lange container cluster-Befehlszeilen.

Kurz gesagt. Auf einem apple/container-Host erstellt und löscht der Gantry-Bereich Cluster Kubernetes-Cluster mit container cluster (CLI 1.6.1 und 1.7) oder container k8s (CLI 1.5.0 bis 1.6.0). In CLI 1.7.1 legt er die Größe der Worker getrennt von der Control Plane fest und schaltet den gemeinsamen Image-Speicher ein. Der Bereich Kubernetes durchsucht den Cluster: Pods, Logs, Shell, Portweiterleitungen, Skalieren und „YAML anwenden“.

Voraussetzungen

  • Ein Mac mit Apple Silicon, macOS 26 und Gantry (brew install --cask getgantry/tap/gantry).
  • Die container-CLI 1.5.0 oder neuer; empfohlen ist 1.7.1. Worker und das CNI Keine brauchen 1.6.0 oder neuer. Worker-Größen und der gemeinsame Image-Speicher brauchen 1.7.0 oder neuer. Verwende das signierte Installationspaket: Dem Homebrew-Build von 1.7.1 fehlen die Cluster-Dienste.
  • kubectl für den Kubernetes-Browser und das Terminal. Gantry kann es mit Homebrew installieren.

Cluster erstellen

  1. Wähle deinen apple/container-Host und öffne Cluster in der Seitenleiste.
  2. Starte einen neuen Cluster und fülle die Optionen unten aus.
  3. Erstelle ihn. Die Liste zeigt den neuen Cluster mit gestreamtem Fortschritt. Abbrechen stoppt die Erstellung und löscht die bereits angelegten Nodes.
OptionCLI-FlagHinweise
Name--nameAuch der Name des Kubeconfig-Kontexts
Worker--workersAnzahl der Worker-Nodes. CLI 1.6.0+
Worker-CPUs und -Arbeitsspeicher--workers count=N,cpus=C,memory=MCLI 1.7+. Vor 1.7 legen --cpus und --memory die Werte für jeden Node fest
CPUs--cpusControl Plane (CLI 1.7+) oder jeder Node (vor 1.7)
Arbeitsspeicher--memoryControl Plane (CLI 1.7+) oder jeder Node (vor 1.7), zum Beispiel 4G
Lokale Images verwenden--shared-image-storeCLI 1.7+. Nodes führen Images aus deinem lokalen Image-Speicher aus
Node-Image--node-imageLeer lassen für den CLI-Standard
CNI--cniStandard (mitgeliefertes kindnet), Keine (NONE, CLI 1.6.0+) oder Pfad zu einem eigenen Manifest

Derselbe Befehl in der CLI:

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Nodes und Cluster-Details

Die Clusterliste zeigt eine Zeile pro Cluster. Die Detailansicht hat eine Übersicht (kubectl-Kontext, API-Server, Kubernetes-Version, Image-Speicher, Worker und ihre Ressourcen, Node-Netzwerk), eine Tabelle Nodes und Untersuchen für die Rohdaten der Nodes. In der Symbolleiste steht Ressourcen durchsuchen, im Menü „Mehr“ Kubeconfig schreiben, kubectl-Kontextbefehl kopieren und Löschen.

Cluster-Nodes sind Container, gehören aber container cluster. Gantry sperrt Starten, Stoppen, Neustarten, Entfernen und Umbenennen für einen Node und sagt dir, warum; „Alle starten“ und „Alle stoppen“ überspringen Nodes. In CLI 1.7 blendet die CLI Nodes außerdem in container list aus. Mit CLI 1.6 oder älter erstellte Cluster erscheinen nicht in der Liste von 1.7; entferne sie mit container cluster delete --name <name>.

Den Cluster durchsuchen

Klicke bei einem laufenden Cluster auf Ressourcen durchsuchen oder öffne Kubernetes in der Seitenleiste. Der Bereich braucht keinen Host und listet jeden Kubeconfig-Kontext; die Kontexte von apple/container-Clustern stehen oben. Wähle einen Namespace oder alle Namespaces und dann eine Art: Pods, Deployments, StatefulSets, DaemonSets, Services, Ingresses, ConfigMaps, Secrets, Nodes oder Ereignisse.

  • Pods: Logs mit Verfolgen, Tail und dem vorherigen Container; eine Shell im Pod; Portweiterleitung an 127.0.0.1.
  • Workloads: Deployments und StatefulSets skalieren; ein Rollout neu starten.
  • Secrets: Werte sind in der Liste und im YAML maskiert, bis du auf „Einblenden“ klickst.
  • YAML anwenden: Manifest einsetzen oder Datei öffnen; Fehler erscheinen im Dialog.

Der Browser führt kubectl aus. Findet Gantry es nicht, zeigt der Bereich brew install kubectl mit einer Taste, die den Befehl ausführt.

kubectl verbinden

Beim Erstellen des Clusters fügt die CLI in ~/.kube/config einen Kontext hinzu, der nach dem Cluster benannt ist. Nutze kubectl-Kontextbefehl kopieren in Gantry oder tippe ihn selbst:

Shell
kubectl --context dev get nodes

Um den Cluster in einer eigenen Datei zu halten, nutze Kubeconfig schreiben. Gantry führt container cluster write-config aus; der Standardpfad ist ~/.kube/<name>.kubeconfig.

Lokale Images im Cluster verwenden

Schalte in CLI 1.7 beim Erstellen des Clusters Lokale Images verwenden ein. Das fügt --shared-image-store hinzu, sodass die Nodes jedes Image, das du mit container baust oder pullst, über seinen Namen ausführen können, ganz ohne Registry. Die Einstellung wird beim Erstellen festgelegt. Nachdem du ein Tag neu gebaut hast, verwende imagePullPolicy: Always oder ein neues Tag. Privilegierte Pods können jedes Image in deinem lokalen Speicher lesen, nutze das also nur für die lokale Entwicklung.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

In CLI 1.5 und 1.6 klickst du unter Images mit der rechten Maustaste auf das Image und wählst In Cluster laden. Gantry führt container cluster load-image aus, das das Image in das containerd jedes Nodes kopiert. CLI 1.7 hat diesen Befehl entfernt, daher blendet Gantry die Aktion dort aus.

Shell
container cluster load-image --name dev myapp:dev

Wenn die Cluster-Dienste nicht antworten

Schlägt ein Cluster-Befehl mit cluster service unavailable fehl, prüft Gantry, wie die CLI installiert ist. Bei einem Homebrew-Build ohne Cluster-Plug-ins erscheint die Meldung, dass dem Build die Cluster-Dienste fehlen, und ein Link Installationsprogramm herunterladen… zum signierten Paket. In anderen Fällen bietet Gantry Dienste neu starten… an.

CNI wählen

Standard ist das mitgelieferte kindnet-Manifest. Wähle Eigenes Manifest, um dein eigenes CNI, zum Beispiel Calico oder Cilium, aus einer Datei zu installieren. Wähle Keine, um später selbst ein CNI zu installieren; bis dahin bleiben die Nodes NotReady.

Kubernetes auf dem Mac mit Apple container ausführen

Apples container-Tool erstellt einen lokalen Kubernetes-Cluster mit einem einzigen Befehl. Jeder Node ist eine leichtgewichtige virtuelle Maschine auf deinem Mac. Diese Anleitung führt von einem leeren Mac bis zu einem laufenden Deployment, zuerst im Terminal und dann in Gantry.

Was du brauchst

  • Einen Mac mit Apple Silicon und macOS 26 oder neuer.
  • Die container-CLI 1.7.1 aus dem signierten .pkg auf der Release-Seite von apple/container. Dem Homebrew-Build von 1.7.1 fehlen die Cluster-Dienste, daher schlägt container cluster mit cluster service unavailable fehl.
  • Etwa 6 GB freien Arbeitsspeicher für das Beispiel unten: drei Nodes mit je 2 GB.
  • kubectl, wenn du den Cluster im Terminal nutzen willst (brew install kubectl).

Starte die Dienste einmal, nachdem du das Paket installiert hast:

Terminal
container system start
    Den Cluster erstellen

Dieser Befehl erstellt einen Cluster namens dev mit einem Control-Plane-Node und zwei Workern. Jeder Node bekommt 2 CPUs und 2 GB Arbeitsspeicher:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M legt die Größe einer Gruppe von Workern fest. Wiederhole es für Gruppen unterschiedlicher Größe. Ohne --workers ist ein einziger Node zugleich Control Plane und Worker.
  • --cpus und --memory legen die Größe der Control Plane fest. Standard ist ein Viertel der CPUs und des Arbeitsspeichers deines Mac, mindestens 2 CPUs und 2 GB.
  • --shared-image-store lässt die Nodes deine lokalen Images verwenden (siehe unten). Du kannst das später nicht ändern: Lösche den Cluster und erstelle ihn neu.
  • --cni ./calico.yaml installiert dein eigenes CNI statt des mitgelieferten kindnet; --cni NONE installiert keines.

Die CLI fügt in ~/.kube/config einen Kontext namens dev hinzu. Prüfe die Nodes:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Ein lokales Image ohne Registry ausführen

Mit --shared-image-store können die Nodes jedes Image aus deinem lokalen container-Image-Speicher ausführen. Baue ein Image und verwende es über seinen Namen:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Hinweis
Nachdem du dasselbe Tag neu gebaut hast, führe kubectl rollout restart mit imagePullPolicy: Always aus oder verwende ein neues Tag. Mit IfNotPresent behält ein Node die Kopie, die er schon hat. Alles mit Root-Rechten auf einem Node kann jedes Image in deinem lokalen Speicher lesen, auch private Images. Nutze den gemeinsamen Speicher also nur für die lokale Entwicklung.

In CLI 1.5 und 1.6 gibt es keinen gemeinsamen Speicher. Verwende dort container cluster load-image oder In Cluster laden in Gantry. CLI 1.7 hat load-image entfernt.

    Die App im Browser öffnen

Leite einen lokalen Port an das Deployment weiter und öffne dann http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Den Cluster stoppen und löschen
Terminal
container cluster delete --name dev

Wenn der Control-Plane-Node stoppt, zum Beispiel nach container system stop, lösche den Cluster und erstelle ihn neu. Erstelle einen Wegwerf-Cluster mit --rm, damit seine Nodes beim Stoppen entfernt werden.

    Häufige Probleme
  • cluster service unavailable: Die CLI ist der Homebrew-Build, oder die Dienste laufen nicht. Installiere das signierte Paket oder starte die Dienste mit container system stop und container system start neu. Gantry zeigt denselben Rat unter „Cluster“.
  • Ein alter Cluster fehlt in der Liste: CLI 1.7 listet keine Cluster, die mit 1.6 oder älter erstellt wurden. Entferne einen solchen Cluster mit container cluster delete --name <name>.
  • Nodes bleiben NotReady: Du hast --cni NONE verwendet. Wende ein CNI-Manifest an.
  • Du kannst einen Node-Container nicht stoppen: Das ist Absicht. container stop und delete verweigern Cluster-Nodes; verwende container cluster delete.
    Im Vergleich zu Docker Desktop und OrbStack

Docker Desktop hat integriertes Kubernetes mit kubeadm (ein Node) oder kind (mehrere Nodes), OrbStack hat einen integrierten Cluster mit einem Node. container cluster führt kubeadm auf kindest/node-Images aus, jeden Node in einer eigenen VM, mit Clustern aus mehreren Nodes und dem gemeinsamen Image-Speicher. Siehe den vollständigen Vergleich.

Cluster per KI-Agent

Der Gantry-MCP-Server bietet list_clusters, create_cluster und delete_cluster. So kann ein Agent wie Claude Code einen temporären Cluster für einen Test anlegen und danach wieder entfernen.

Gantry-MCP-Server hinzufügen
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Fragen und Antworten

Unterstützt Apple container Kubernetes?

Ja. Die container-CLI erstellt Kubernetes-Cluster, deren Nodes als Container laufen: container cluster in CLI 1.6.1 und 1.7, container k8s in CLI 1.5.0 bis 1.6.0. Gantry liefert die GUI dazu.

Unterstützt Gantry container cluster?

Ja. Gantry listet, erstellt und löscht Cluster auf apple/container-Hosts, zeigt ihre Nodes, schreibt die Kubeconfig und öffnet den Cluster im Kubernetes-Browser. In CLI 1.7 legt es außerdem die Größe der Worker fest und schaltet den gemeinsamen Image-Speicher ein. Je nach CLI-Version verwendet es cluster oder k8s.

Wie nutze ich kubectl mit einem apple/container-Cluster?

Beim Erstellen eines Clusters fügt die CLI in ~/.kube/config einen Kubeconfig-Kontext hinzu, der nach dem Cluster benannt ist. Führe kubectl --context <name> get nodes aus. Für eine separate Datei nutzt du Kubeconfig schreiben in Gantry; der Standardpfad ist ~/.kube/<name>.kubeconfig.

Wie bekomme ich ein lokales Image ohne Registry in den Cluster?

Erstelle den Cluster in CLI 1.7 mit Lokale Images verwenden (--shared-image-store). Pods führen dann die Images, die du mit container baust oder pullst, über ihren Namen aus. In CLI 1.5 und 1.6 klickst du unter „Images“ mit der rechten Maustaste auf das Image und wählst In Cluster laden; Gantry führt container cluster load-image aus. CLI 1.7 hat load-image entfernt.

Kann ich einen Cluster mit mehreren Nodes erstellen?

Ja. Lege die Anzahl der Worker im Dialog zum Erstellen fest; Worker brauchen CLI 1.6.0 oder neuer. In CLI 1.7 legst du außerdem CPUs und Arbeitsspeicher der Worker getrennt von der Control Plane fest.

Kann ich ein eigenes CNI wie Calico oder Cilium verwenden?

Ja. Wähle Eigenes Manifest und dann die Manifest-Datei, oder wähle Keine und installiere nach dem Start des Clusters selbst ein CNI. Die Nodes bleiben NotReady, bis ein CNI läuft. Keine erfordert CLI 1.6.0 oder neuer. Das Standard-CNI ist das mitgelieferte kindnet-Manifest.

Warum meldet Gantry, dass die Cluster-Dienste nicht verfügbar sind?

Die container-Dienste haben auf einen Cluster-Befehl nicht geantwortet. Ist deine CLI ein Homebrew-Build ohne Cluster-Dienste, sagt Gantry das und verlinkt das signierte Installationsprogramm auf der Release-Seite von apple/container. Sonst bietet es Dienste neu starten an.

Brauche ich kubectl, um den Cluster in Gantry zu nutzen?

Im Moment ja: Der Kubernetes-Browser von Gantry führt kubectl aus. Ist es nicht installiert, zeigt der Browser den Befehl brew install kubectl und kann ihn für dich ausführen.

Kann ich Kubernetes auf dem Mac ohne Docker ausführen?

Ja. Apples container-CLI erstellt Kubernetes-Cluster selbst mit container cluster create. Jeder Node läuft als leichtgewichtige VM, und du brauchst weder Docker noch Docker Desktop, kind oder minikube.

Wie viele Nodes kann ein container cluster haben?

Eine Control Plane und so viele Worker, wie CPUs und Arbeitsspeicher deines Mac hergeben. Lege sie mit --workers fest; in CLI 1.7 kann jede Gruppe von Workern eigene CPUs und eigenen Arbeitsspeicher haben.

Welche Kubernetes-Version verwendet container cluster?

CLI 1.7.1 verwendet standardmäßig das Node-Image kindest/node:v1.35.5. Wähle mit --node-image eine andere Version, zum Beispiel docker.io/kindest/node:v1.34.11. Gantry zeigt die Version in der Cluster-Übersicht.
