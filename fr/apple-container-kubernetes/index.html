Gantry/Kubernetes sur apple/container

Kubernetes sur Apple container

apple/container peut exécuter un cluster Kubernetes dont les nœuds sont des conteneurs sur votre Mac. Gantry en est une GUI : créez un cluster, regardez ses nœuds démarrer, exécutez-y vos images locales et parcourez ses pods, journaux et services, sans longues lignes de commande container cluster.

En bref. Sur un hôte apple/container, la section Clusters de Gantry crée et supprime des clusters Kubernetes avec container cluster (CLI 1.6.1 et 1.7) ou container k8s (CLI 1.5.0 à 1.6.0). Avec la CLI 1.7.1, elle dimensionne les workers indépendamment du plan de contrôle et active le stockage d'images partagé. La section Kubernetes parcourt le cluster : pods, journaux, shell, redirections de port, mise à l'échelle et application de YAML.

Prérequis

  • Un Mac à puce Apple, macOS 26 et Gantry (brew install --cask getgantry/tap/gantry).
  • La CLI container 1.5.0 ou ultérieure ; la 1.7.1 est recommandée. Les workers et le CNI Aucun nécessitent la 1.6.0 ou ultérieure. La taille des workers et le stockage d'images partagé nécessitent la 1.7.0 ou ultérieure. Utilisez le paquet d'installation signé : le build Homebrew de la 1.7.1 n'a pas de services de cluster.
  • kubectl pour le navigateur Kubernetes et le terminal. Gantry peut l'installer avec Homebrew.

Créer un cluster

  1. Sélectionnez votre hôte apple/container et ouvrez Clusters dans la barre latérale.
  2. Lancez la création d'un cluster et renseignez les options ci-dessous.
  3. Créez-le. La liste affiche le nouveau cluster avec la progression en continu. Annuler arrête la création et supprime les nœuds déjà créés.
OptionOption de la CLIRemarques
Nom--nameSert aussi de nom au contexte kubeconfig
Workers--workersNombre de nœuds worker. CLI 1.6.0+
CPU et mémoire des workers--workers count=N,cpus=C,memory=MCLI 1.7+. Avant la 1.7, --cpus et --memory s'appliquent à chaque nœud
CPU--cpusPlan de contrôle (CLI 1.7+) ou chaque nœud (avant la 1.7)
Mémoire--memoryPlan de contrôle (CLI 1.7+) ou chaque nœud (avant la 1.7), par exemple 4G
Utiliser les images locales--shared-image-storeCLI 1.7+. Les nœuds exécutent les images de votre stockage d'images local
Image des nœuds--node-imageVide : valeur par défaut de la CLI
CNI--cniPar défaut (kindnet intégré), Aucun (NONE, CLI 1.6.0+) ou chemin d'un manifeste personnalisé

La même commande dans la CLI :

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Nœuds et détails du cluster

La liste des clusters affiche une ligne par cluster. La vue détaillée comprend un Aperçu (contexte kubectl, serveur API, version de Kubernetes, stockage d'images, workers et leurs ressources, réseau des nœuds), un tableau Nœuds et Inspecter pour les données brutes des nœuds. La barre d'outils contient Parcourir les ressources, et le menu Plus contient Écrire le kubeconfig, Copier la commande de contexte kubectl et Supprimer.

Les nœuds d'un cluster sont des conteneurs, mais c'est container cluster qui les gère. Gantry désactive le démarrage, l'arrêt, le redémarrage, la suppression et le renommage d'un nœud et vous explique pourquoi ; Tout démarrer et Tout arrêter ignorent les nœuds. Avec la CLI 1.7, la CLI masque aussi les nœuds dans container list. Les clusters créés avec la CLI 1.6 ou antérieure n'apparaissent pas dans la liste de la 1.7 ; supprimez-les avec container cluster delete --name <name>.

Parcourir le cluster

Cliquez sur Parcourir les ressources sur un cluster en cours d'exécution, ou ouvrez Kubernetes dans la barre latérale. La section ne nécessite aucun hôte et liste tous les contextes kubeconfig ; les contextes des clusters apple/container apparaissent en premier. Choisissez un espace de noms ou tous les espaces de noms, puis un type : pods, Deployments, StatefulSets, DaemonSets, services, Ingress, ConfigMaps, secrets, nœuds ou événements.

  • Pods : journaux avec suivi, fin du journal et conteneur précédent ; shell dans le pod ; redirection de port vers 127.0.0.1.
  • Charges de travail : mise à l'échelle des Deployments et StatefulSets ; redémarrage d'un rollout.
  • Secrets : les valeurs sont masquées dans la liste et dans le YAML jusqu'à ce que vous cliquiez sur Afficher.
  • Appliquer un YAML : collez un manifeste ou ouvrez un fichier ; les erreurs s'affichent dans la feuille.

Le navigateur exécute kubectl. Si Gantry ne le trouve pas, la section affiche brew install kubectl avec un bouton qui exécute la commande. Un client Kubernetes natif qui se passe de kubectl est en développement.

Connecter kubectl

Lorsqu'elle crée le cluster, la CLI ajoute à ~/.kube/config un contexte qui porte son nom. Utilisez Copier la commande de contexte kubectl dans Gantry, ou tapez-la :

Shell
kubectl --context dev get nodes

Pour garder le cluster dans son propre fichier, utilisez Écrire le kubeconfig. Gantry exécute container cluster write-config ; le chemin par défaut est ~/.kube/<name>.kubeconfig.

Utiliser les images locales dans le cluster

Avec la CLI 1.7, activez Utiliser les images locales lors de la création du cluster. L'option ajoute --shared-image-store : les nœuds peuvent exécuter par son nom toute image que vous construisez ou téléchargez avec container, sans registre. Ce réglage est fixé à la création. Après avoir reconstruit un tag, utilisez imagePullPolicy: Always ou un nouveau tag. Les pods privilégiés peuvent lire toutes les images de votre stockage local : réservez cette option au développement local.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

Avec les CLI 1.5 et 1.6, faites un clic droit sur l'image dans Images et choisissez Charger dans le cluster. Gantry exécute container cluster load-image, qui copie l'image dans le containerd de chaque nœud. La CLI 1.7 a supprimé cette commande ; Gantry y masque donc l'action.

Shell
container cluster load-image --name dev myapp:dev

Quand les services de cluster ne répondent pas

Si une commande de cluster échoue avec cluster service unavailable, Gantry vérifie comment la CLI est installée. Pour un build Homebrew sans les plug-ins de cluster, il indique que ce build n'a pas les services de cluster et affiche un lien Télécharger le programme d'installation… vers le paquet signé. Dans les autres cas, Gantry propose Redémarrer les services….

Choisir un CNI

Par défaut, c'est le manifeste kindnet intégré. Choisissez Manifeste personnalisé pour installer votre propre CNI depuis un fichier, par exemple Calico ou Cilium. Choisissez Aucun pour installer vous-même un CNI plus tard ; d'ici là, les nœuds restent NotReady.

Des clusters pilotés par les agents IA

Le serveur MCP de Gantry propose list_clusters, create_cluster et delete_cluster : un agent comme Claude Code peut créer un cluster temporaire pour un test, puis le supprimer.

Ajouter le serveur MCP de Gantry
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

En savoir plus sur apple/container

Pour un guide pas à pas depuis le terminal, lisez Exécuter Kubernetes sur un Mac avec Apple container. Lisez le guide apple/container pour chaque commande container et sa fonctionnalité dans Gantry, ou voyez comment Gantry se compare à Docker Desktop, OrbStack et Podman Desktop.

Questions et réponses

Apple container prend-il en charge Kubernetes ?

Oui. La CLI container crée des clusters Kubernetes dont les nœuds tournent comme des conteneurs : container cluster dans les CLI 1.6.1 et 1.7, container k8s dans les CLI 1.5.0 à 1.6.0. Gantry y ajoute une GUI.

Gantry prend-il en charge container cluster ?

Oui. Gantry liste, crée et supprime des clusters sur les hôtes apple/container, affiche leurs nœuds, écrit le kubeconfig et ouvre le cluster dans son navigateur Kubernetes. Avec la CLI 1.7, il dimensionne aussi les workers et active le stockage d'images partagé. Il utilise cluster ou k8s selon votre version de la CLI.

Comment utiliser kubectl avec un cluster apple/container ?

Quand la CLI crée un cluster, elle ajoute à ~/.kube/config un contexte kubeconfig qui porte le nom du cluster. Exécutez kubectl --context <name> get nodes. Pour garder un fichier séparé, utilisez Écrire le kubeconfig dans Gantry ; le chemin par défaut est ~/.kube/<name>.kubeconfig.

Comment charger une image locale dans le cluster sans registre ?

Avec la CLI 1.7, créez le cluster avec Utiliser les images locales (--shared-image-store). Les pods exécutent alors par leur nom les images que vous construisez ou téléchargez avec container. Avec les CLI 1.5 et 1.6, faites un clic droit sur l'image dans Images et choisissez Charger dans le cluster ; Gantry exécute container cluster load-image. La CLI 1.7 a supprimé load-image.

Peut-on créer un cluster à plusieurs nœuds ?

Oui. Indiquez le nombre de workers dans la feuille de création ; les workers nécessitent la CLI 1.6.0 ou ultérieure. Avec la CLI 1.7, vous réglez aussi les CPU et la mémoire des workers indépendamment du plan de contrôle.

Peut-on utiliser son propre CNI, comme Calico ou Cilium ?

Oui. Choisissez Manifeste personnalisé et sélectionnez le fichier manifeste, ou choisissez Aucun et appliquez vous-même un CNI une fois le cluster démarré. Les nœuds restent NotReady tant qu'aucun CNI ne tourne. Aucun nécessite la CLI 1.6.0 ou ultérieure. Le CNI par défaut est le manifeste kindnet intégré.

Pourquoi Gantry indique-t-il que les services de cluster sont indisponibles ?

Les services container n'ont pas répondu à une commande de cluster. Si votre CLI est un build Homebrew sans les services de cluster, Gantry le signale et propose un lien vers le programme d'installation signé sur la page des versions d'apple/container. Sinon, il propose Redémarrer les services.

Faut-il kubectl pour utiliser le cluster dans Gantry ?

Pour l'instant, oui : le navigateur Kubernetes de Gantry exécute kubectl. S'il n'est pas installé, le navigateur affiche la commande brew install kubectl et peut l'exécuter pour vous. Un client Kubernetes natif qui supprime cette étape est en développement.
