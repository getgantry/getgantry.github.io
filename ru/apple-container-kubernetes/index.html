Gantry/Kubernetes на apple/container

Kubernetes на Apple container

apple/container может запустить кластер Kubernetes, узлы которого — контейнеры на вашем Mac. Gantry — GUI для этого: создайте кластер, следите, как поднимаются узлы, запускайте в нём свои локальные образы и просматривайте его поды, логи и сервисы без длинных команд container cluster.

Коротко. На хосте apple/container раздел Кластеры в Gantry создаёт и удаляет кластеры Kubernetes командой container cluster (CLI 1.6.1 и 1.7) или container k8s (CLI от 1.5.0 до 1.6.0). В CLI 1.7.1 он задаёт размер рабочих узлов отдельно от управляющего узла и включает общее хранилище образов. Раздел Kubernetes показывает содержимое кластера: поды, логи, оболочку, проброс портов, масштабирование и «Применить YAML».

Требования

  • Mac с Apple silicon, macOS 26 и Gantry (brew install --cask getgantry/tap/gantry).
  • CLI container версии 1.5.0 или новее; рекомендуется 1.7.1. Для рабочих узлов и CNI Нет нужна 1.6.0 или новее. Для размеров рабочих узлов и общего хранилища образов нужна 1.7.0 или новее. Используйте подписанный установочный пакет: в сборке Homebrew версии 1.7.1 нет служб кластера.
  • kubectl для браузера Kubernetes и терминала. Gantry может установить его через Homebrew.

Создание кластера

  1. Выберите хост apple/container и откройте Кластеры в боковом меню.
  2. Начните создание нового кластера и заполните параметры ниже.
  3. Создайте его. Новый кластер появится в списке, где в реальном времени виден ход создания. Отменить останавливает создание и удаляет уже созданные узлы.
ПараметрФлаг CLIПримечания
Имя--nameТакже имя контекста kubeconfig
Рабочие узлы--workersЧисло рабочих узлов. CLI 1.6.0+
CPU и память рабочих узлов--workers count=N,cpus=C,memory=MCLI 1.7+. До 1.7 --cpus и --memory задают все узлы
CPU--cpusУправляющий узел (CLI 1.7+) или каждый узел (до 1.7)
Память--memoryУправляющий узел (CLI 1.7+) или каждый узел (до 1.7), например 4G
Использовать локальные образы--shared-image-storeCLI 1.7+. Узлы запускают образы из вашего локального хранилища образов
Образ узла--node-imageПустое поле — значение CLI по умолчанию
CNI--cniПо умолчанию (встроенный kindnet), «Нет» (NONE, CLI 1.6.0+) или путь к своему манифесту

Та же команда в CLI:

Терминал
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Узлы и сведения о кластере

В списке кластеров — одна строка на кластер. В подробном виде есть Обзор (контекст kubectl, API-сервер, версия Kubernetes, хранилище образов, рабочие узлы и их ресурсы, сеть узлов), таблица Узлы и Инспекция с исходными данными узлов. На панели инструментов есть Просмотреть ресурсы, а в меню «Ещё» — Записать kubeconfig, Скопировать команду контекста kubectl и Удалить.

Узлы кластера — это контейнеры, но ими управляет container cluster. Gantry отключает для узла запуск, остановку, перезапуск, удаление и переименование и объясняет почему, а «Запустить все» и «Остановить все» пропускают узлы. В CLI 1.7 сам CLI тоже скрывает узлы из container list. Кластеры, созданные в CLI 1.6 или раньше, не видны в списке 1.7; удалите их командой container cluster delete --name <name>.

Просмотр кластера

Нажмите Просмотреть ресурсы у запущенного кластера или откройте Kubernetes в боковом меню. Разделу не нужен хост, и он показывает все контексты kubeconfig; контексты кластеров apple/container идут первыми. Выберите пространство имён или все пространства имён, затем тип объекта: поды, Deployments, StatefulSets, DaemonSets, сервисы, Ingress, ConfigMaps, секреты, узлы или события.

  • Поды: логи с отслеживанием, последними строками и предыдущим контейнером; оболочка в поде; проброс порта на 127.0.0.1.
  • Рабочие нагрузки: масштабирование Deployments и StatefulSets; перезапуск развёртывания.
  • Секреты: значения скрыты в списке и в YAML, пока вы не нажмёте «Показать».
  • Применить YAML: вставьте манифест или откройте файл; ошибки видны прямо в окне.

Браузер запускает kubectl. Если Gantry не находит его, раздел показывает brew install kubectl и кнопку, которая выполняет эту команду.

Подключение kubectl

При создании кластера CLI добавляет в ~/.kube/config контекст с именем кластера. Нажмите Скопировать команду контекста kubectl в Gantry или введите команду сами:

Терминал
kubectl --context dev get nodes

Чтобы хранить кластер в отдельном файле, нажмите Записать kubeconfig. Gantry выполнит container cluster write-config; путь по умолчанию — ~/.kube/<name>.kubeconfig.

Локальные образы в кластере

В CLI 1.7 включите Использовать локальные образы при создании кластера. Это добавляет --shared-image-store, и узлы могут запускать по имени любой образ, который вы собрали или скачали с помощью container, без реестра. Настройка задаётся при создании и потом не меняется. После пересборки тега используйте imagePullPolicy: Always или новый тег. Привилегированные поды могут читать все образы в вашем локальном хранилище, поэтому используйте это только для локальной разработки.

Терминал
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

В CLI 1.5 и 1.6 нажмите на образ в разделе Образы правой кнопкой и выберите Загрузить в кластер. Gantry выполнит container cluster load-image: команда копирует образ в containerd каждого узла. В CLI 1.7 этой команды нет, поэтому там Gantry скрывает это действие.

Терминал
container cluster load-image --name dev myapp:dev

Если службы кластера не отвечают

Если команда кластера завершается ошибкой cluster service unavailable, Gantry проверяет, как установлен CLI. Для сборки Homebrew без плагинов кластера он сообщает, что в сборке нет служб кластера, и даёт ссылку Скачать установщик… на подписанный пакет. В остальных случаях Gantry предлагает Перезапустить службы….

Выбор CNI

По умолчанию используется встроенный манифест kindnet. Выберите Свой манифест, чтобы установить свой CNI из файла, например Calico или Cilium. Выберите Нет, чтобы установить CNI позже самостоятельно; до этого узлы остаются в состоянии NotReady.

Kubernetes на Mac с Apple container

Инструмент container от Apple создаёт локальный кластер Kubernetes одной командой. Каждый узел — лёгкая виртуальная машина на вашем Mac. Это руководство ведёт от пустого Mac до работающего Deployment: сначала в терминале, затем в Gantry.

Что нужно

  • Mac с Apple silicon и macOS 26 или новее.
  • CLI container 1.7.1 из подписанного пакета .pkg на странице релизов apple/container. В сборке Homebrew версии 1.7.1 нет служб кластера, поэтому container cluster завершается ошибкой cluster service unavailable.
  • Около 6 ГБ свободной памяти для примера ниже: три узла по 2 ГБ.
  • kubectl, если вы хотите работать с кластером из терминала (brew install kubectl).

После установки пакета один раз запустите службы:

Терминал
container system start
    Создание кластера

Эта команда создаёт кластер dev с одним управляющим узлом и двумя рабочими. Каждый узел получает 2 CPU и 2 ГБ памяти:

Терминал
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M задаёт группу рабочих узлов одного размера. Для групп разного размера повторите флаг. Без --workers один узел — одновременно управляющий и рабочий.
  • --cpus и --memory задают размер управляющего узла. По умолчанию это четверть CPU и памяти вашего Mac, но не меньше 2 CPU и 2 ГБ.
  • --shared-image-store позволяет узлам использовать ваши локальные образы (см. ниже). Изменить это позже нельзя: удалите кластер и создайте его заново.
  • --cni ./calico.yaml устанавливает ваш CNI вместо встроенного kindnet; --cni NONE не устанавливает никакого.

CLI добавляет в ~/.kube/config контекст dev. Проверьте узлы:

Терминал
container cluster list --nodes
kubectl --context dev get nodes
    Локальный образ без реестра

С --shared-image-store узлы могут запускать любой образ из вашего локального хранилища образов container. Соберите образ и используйте его по имени:

Терминал
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Примечание
После пересборки того же тега выполните kubectl rollout restart с imagePullPolicy: Always или используйте новый тег. С IfNotPresent узел оставляет уже имеющуюся копию. Всё, что имеет root-доступ на узле, может читать все образы вашего локального хранилища, включая приватные, поэтому используйте общее хранилище только для локальной разработки.

В CLI 1.5 и 1.6 общего хранилища нет. Там используйте container cluster load-image или Загрузить в кластер в Gantry. В CLI 1.7 команды load-image больше нет.

    Откройте приложение в браузере

Пробросьте локальный порт на Deployment, затем откройте http://localhost:8080:

Терминал
kubectl --context dev port-forward deployment/hello 8080:80
    Остановка и удаление кластера
Терминал
container cluster delete --name dev

Если управляющий узел остановился, например после container system stop, удалите кластер и создайте его заново. Временный кластер создавайте с --rm: его узлы удалятся, когда остановятся.

    Частые проблемы
  • cluster service unavailable: CLI установлен из Homebrew или службы не запущены. Установите подписанный пакет или перезапустите службы командами container system stop и container system start. Gantry даёт тот же совет в разделе «Кластеры».
  • Старого кластера нет в списке: CLI 1.7 не показывает кластеры, созданные в 1.6 или раньше. Удалите такой кластер командой container cluster delete --name <name>.
  • Узлы остаются NotReady: вы использовали --cni NONE. Примените манифест CNI.
  • Контейнер узла не останавливается: так задумано. container stop и delete отказываются работать с узлами кластера; используйте container cluster delete.
    Сравнение с Docker Desktop и OrbStack

В Docker Desktop есть встроенный Kubernetes на kubeadm (один узел) или kind (несколько узлов), а в OrbStack — встроенный кластер из одного узла. container cluster запускает kubeadm на образах kindest/node, каждый узел в своей ВМ, с кластерами из нескольких узлов и общим хранилищем образов. См. полное сравнение.

Управление кластерами через ИИ-агентов

В MCP-сервере Gantry есть list_clusters, create_cluster и delete_cluster, поэтому агент вроде Claude Code может создать временный кластер для теста и потом удалить его.

Подключите MCP-сервер Gantry
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Ещё об apple/container

Пошаговое руководство с работой в терминале — Kubernetes на Mac с Apple container. В руководстве по apple/container описана каждая команда container и соответствующая функция Gantry. Там же можно узнать, чем Gantry отличается от Docker Desktop, OrbStack и Podman Desktop.

Вопросы и ответы

Поддерживает ли Apple container Kubernetes?

Да. CLI container создаёт кластеры Kubernetes, узлы которых работают как контейнеры: container cluster в CLI 1.6.1 и 1.7, container k8s в CLI от 1.5.0 до 1.6.0. Gantry даёт для этого GUI.

Поддерживает ли Gantry container cluster?

Да. Gantry показывает, создаёт и удаляет кластеры на хостах apple/container, показывает их узлы, записывает kubeconfig и открывает кластер в своём браузере Kubernetes. В CLI 1.7 он также задаёт размер рабочих узлов и включает общее хранилище образов. Он использует cluster или k8s в зависимости от версии CLI.

Как подключить kubectl к кластеру apple/container?

При создании кластера CLI добавляет в ~/.kube/config контекст kubeconfig с именем кластера. Выполните kubectl --context <name> get nodes. Чтобы держать kubeconfig в отдельном файле, нажмите Записать kubeconfig в Gantry; путь по умолчанию — ~/.kube/<name>.kubeconfig.

Как загрузить локальный образ в кластер без реестра?

В CLI 1.7 создайте кластер с параметром Использовать локальные образы (--shared-image-store). Тогда поды запускают по имени образы, которые вы собрали или скачали с помощью container. В CLI 1.5 и 1.6 нажмите на образ в разделе «Образы» правой кнопкой и выберите Загрузить в кластер; Gantry выполнит container cluster load-image. В CLI 1.7 команды load-image больше нет.

Можно ли создать кластер из нескольких узлов?

Да. Укажите число рабочих узлов в окне создания; для рабочих узлов нужен CLI 1.6.0 или новее. В CLI 1.7 вы также задаёте CPU и память рабочих узлов отдельно от управляющего узла.

Можно ли использовать свой CNI, например Calico или Cilium?

Да. Выберите Свой манифест и укажите файл манифеста или выберите Нет и установите CNI сами после запуска кластера. Пока CNI не работает, узлы остаются в состоянии NotReady. Для Нет нужен CLI 1.6.0 или новее. CNI по умолчанию — встроенный манифест kindnet.

Почему Gantry сообщает, что службы кластера недоступны?

Службы container не ответили на команду кластера. Если ваш CLI — сборка Homebrew без служб кластера, Gantry сообщает об этом и даёт ссылку на подписанный установщик на странице релизов apple/container. В остальных случаях он предлагает Перезапустить службы.

Нужен ли kubectl, чтобы работать с кластером в Gantry?

Пока да: браузер Kubernetes в Gantry запускает kubectl. Если он не установлен, браузер показывает команду brew install kubectl и может выполнить её за вас.

Можно ли запустить Kubernetes на Mac без Docker?

Да. CLI container от Apple сам создаёт кластеры Kubernetes командой container cluster create. Каждый узел работает как лёгкая ВМ, и вам не нужны Docker, Docker Desktop, kind или minikube.

Сколько узлов может быть в container cluster?

Один управляющий узел и столько рабочих, сколько позволяют CPU и память вашего Mac. Задайте их флагом --workers; в CLI 1.7 у каждой группы рабочих узлов могут быть свои CPU и память.

Какую версию Kubernetes использует container cluster?

CLI 1.7.1 по умолчанию использует образ узла kindest/node:v1.35.5. Другую версию выберите флагом --node-image, например docker.io/kindest/node:v1.34.11. Gantry показывает версию в обзоре кластера.
