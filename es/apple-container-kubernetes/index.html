Gantry/Kubernetes en apple/container

Kubernetes en Apple container

apple/container puede ejecutar un clúster de Kubernetes cuyos nodos son contenedores en tu Mac. Gantry es una GUI para ello: crea un clúster, observa cómo arrancan sus nodos, ejecuta en él tus imágenes locales y explora sus pods, logs y servicios, sin largas líneas de comando de container cluster.

En resumen. En un host apple/container, la sección Clústeres de Gantry crea y elimina clústeres de Kubernetes con container cluster (CLI 1.6.1 y 1.7) o container k8s (CLI 1.5.0 a 1.6.0). En la CLI 1.7.1 define el tamaño de los workers por separado del plano de control y activa el almacén de imágenes compartido. La sección Kubernetes explora el clúster: pods, logs, shell, reenvío de puertos, escalado y Aplicar YAML.

Requisitos

  • Un Mac con chip de Apple, macOS 26 y Gantry (brew install --cask getgantry/tap/gantry).
  • La CLI container 1.5.0 o posterior; se recomienda la 1.7.1. Los workers y la CNI Ninguno requieren la 1.6.0 o posterior. El tamaño de los workers y el almacén de imágenes compartido requieren la 1.7.0 o posterior. Usa el paquete de instalación firmado: la versión de Homebrew de la 1.7.1 no tiene servicios de clúster.
  • kubectl para el navegador de Kubernetes y el terminal. Gantry puede instalarlo con Homebrew.

Crear un clúster

  1. Selecciona tu host apple/container y abre Clústeres en la barra lateral.
  2. Empieza un clúster nuevo y rellena las opciones de abajo.
  3. Créalo. La lista muestra el clúster nuevo con el progreso en directo. Cancelar detiene la creación y elimina los nodos ya creados.
OpciónParámetro de la CLINotas
Nombre--nameTambién es el nombre del contexto de kubeconfig
Workers--workersNúmero de nodos worker. CLI 1.6.0+
CPU y memoria de los workers--workers count=N,cpus=C,memory=MCLI 1.7+. Antes de la 1.7, --cpus y --memory se aplican a todos los nodos
CPU--cpusPlano de control (CLI 1.7+) o todos los nodos (antes de la 1.7)
Memoria--memoryPlano de control (CLI 1.7+) o todos los nodos (antes de la 1.7), por ejemplo 4G
Usar imágenes locales--shared-image-storeCLI 1.7+. Los nodos ejecutan imágenes de tu almacén de imágenes local
Imagen de nodo--node-imageSi se deja vacía, se usa la predeterminada de la CLI
CNI--cniPredeterminado (kindnet incluido), Ninguno (NONE, CLI 1.6.0+) o la ruta de un manifiesto personalizado

El mismo comando en la CLI:

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Nodos y detalles del clúster

La lista de clústeres muestra una fila por clúster. La vista de detalle tiene un Resumen (contexto de kubectl, servidor de API, versión de Kubernetes, almacén de imágenes, workers y sus recursos, red de nodos), una tabla de Nodos e Inspeccionar para los datos en bruto de los nodos. La barra de herramientas tiene Explorar recursos, y el menú Más tiene Escribir kubeconfig, Copiar comando de contexto de kubectl y Eliminar.

Los nodos del clúster son contenedores, pero los gestiona container cluster. Gantry desactiva iniciar, detener, reiniciar, eliminar y renombrar en un nodo y te explica por qué, e Iniciar todo y Detener todo omiten los nodos. En la CLI 1.7, la CLI también oculta los nodos en container list. Los clústeres creados con la CLI 1.6 o anterior no aparecen en la lista de la 1.7; elimínalos con container cluster delete --name <name>.

Explorar el clúster

Haz clic en Explorar recursos en un clúster en ejecución, o abre Kubernetes en la barra lateral. La sección no necesita host y lista todos los contextos de kubeconfig; los contextos de los clústeres de apple/container aparecen primero. Elige un espacio de nombres o todos, y después un tipo: Pods, Deployments, StatefulSets, DaemonSets, servicios, Ingress, ConfigMaps, secretos, nodos o eventos.

  • Pods: logs con seguimiento, últimas líneas y el contenedor anterior; un shell en el pod; reenvío de puertos a 127.0.0.1.
  • Cargas de trabajo: escalar Deployments y StatefulSets; reiniciar un despliegue.
  • Secretos: los valores aparecen ocultos en la lista y en el YAML hasta que haces clic en Mostrar.
  • Aplicar YAML: pega un manifiesto o abre un archivo; los errores aparecen en la hoja.

El navegador ejecuta kubectl. Si Gantry no lo encuentra, la sección muestra brew install kubectl con un botón que lo ejecuta.

Conectar kubectl

Al crear el clúster, la CLI añade a ~/.kube/config un contexto con el nombre del clúster. Usa Copiar comando de contexto de kubectl en Gantry, o escríbelo:

Shell
kubectl --context dev get nodes

Para tener el clúster en su propio archivo, usa Escribir kubeconfig. Gantry ejecuta container cluster write-config; la ruta predeterminada es ~/.kube/<name>.kubeconfig.

Usar imágenes locales en el clúster

En la CLI 1.7, activa Usar imágenes locales al crear el clúster. Añade --shared-image-store, de modo que los nodos pueden ejecutar por su nombre cualquier imagen que compiles o descargues con container, sin registro. El ajuste queda fijo al crear el clúster. Después de recompilar un tag, usa imagePullPolicy: Always o un tag nuevo. Los pods con privilegios pueden leer todas las imágenes de tu almacén local, así que reserva esta opción para el desarrollo local.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

En las CLI 1.5 y 1.6, haz clic derecho en la imagen en Imágenes y elige Cargar en el clúster. Gantry ejecuta container cluster load-image, que copia la imagen en el containerd de cada nodo. La CLI 1.7 eliminó este comando, así que ahí Gantry oculta la acción.

Shell
container cluster load-image --name dev myapp:dev

Cuando los servicios de clúster no responden

Si un comando de clúster falla con cluster service unavailable, Gantry comprueba cómo está instalada la CLI. Con una versión de Homebrew sin los plugins de clúster, muestra el mensaje de que a esa versión le faltan los servicios de clúster y un enlace Descargar instalador… al paquete firmado. En los demás casos, Gantry ofrece Reiniciar servicios….

Elegir una CNI

La predeterminada es el manifiesto de kindnet incluido. Elige Manifiesto personalizado para instalar tu propia CNI desde un archivo, por ejemplo Calico o Cilium. Elige Ninguno para instalar tú una CNI más adelante; hasta entonces, los nodos siguen en NotReady.

Ejecutar Kubernetes en un Mac con Apple container

La herramienta container de Apple puede crear un clúster local de Kubernetes con un solo comando. Cada nodo es una máquina virtual ligera en tu Mac. Esta guía va de un Mac vacío a un Deployment en ejecución, primero en el terminal y después en Gantry.

Qué necesitas

  • Un Mac con chip de Apple y macOS 26 o posterior.
  • La CLI container 1.7.1 del .pkg firmado de la página de versiones de apple/container. La versión de Homebrew de la 1.7.1 no incluye los servicios de clúster, así que container cluster falla con cluster service unavailable.
  • Unos 6 GB de memoria libre para el ejemplo de abajo: tres nodos de 2 GB cada uno.
  • kubectl, si quieres usar el clúster desde el terminal (brew install kubectl).

Inicia los servicios una vez después de instalar el paquete:

Terminal
container system start
    Crear el clúster

Este comando crea un clúster llamado dev con un nodo de plano de control y dos workers. Cada nodo recibe 2 CPU y 2 GB de memoria:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M define el tamaño de un grupo de workers. Repítelo para grupos de distinto tamaño. Sin --workers, un solo nodo hace de plano de control y de worker.
  • --cpus y --memory definen el tamaño del plano de control. El valor predeterminado es una cuarta parte de la CPU y la memoria de tu Mac, como mínimo 2 CPU y 2 GB.
  • --shared-image-store permite que los nodos usen tus imágenes locales (más abajo). No se puede cambiar después: elimina el clúster y vuelve a crearlo.
  • --cni ./calico.yaml instala tu propia CNI en lugar del kindnet incluido; --cni NONE no instala ninguna.

La CLI añade a ~/.kube/config un contexto llamado dev. Comprueba los nodos:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Ejecutar una imagen local sin registro

Con --shared-image-store, los nodos pueden ejecutar cualquier imagen de tu almacén de imágenes local de container. Compila una imagen y úsala por su nombre:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Nota
Después de recompilar el mismo tag, ejecuta kubectl rollout restart con imagePullPolicy: Always, o usa un tag nuevo. Con IfNotPresent, un nodo se queda con la copia que ya tiene. Cualquier proceso con root en un nodo puede leer todas las imágenes de tu almacén local, también las privadas, así que usa el almacén compartido solo para el desarrollo local.

En las CLI 1.5 y 1.6 no hay almacén compartido. Ahí, usa container cluster load-image o Cargar en el clúster en Gantry. La CLI 1.7 eliminó load-image.

    Abrir la app en un navegador

Reenvía un puerto local al Deployment y abre http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Detener y eliminar el clúster
Terminal
container cluster delete --name dev

Si el nodo del plano de control se detiene, por ejemplo después de container system stop, elimina el clúster y vuelve a crearlo. Crea un clúster desechable con --rm para que sus nodos se eliminen cuando se detengan.

    Problemas habituales
  • cluster service unavailable: la CLI es la versión de Homebrew o los servicios no están en ejecución. Instala el paquete firmado o reinicia los servicios con container system stop y container system start. Gantry muestra el mismo consejo en Clústeres.
  • Falta un clúster antiguo en la lista: la CLI 1.7 no lista los clústeres creados con la 1.6 o anterior. Elimina uno con container cluster delete --name <name>.
  • Los nodos siguen en NotReady: has usado --cni NONE. Aplica un manifiesto de CNI.
  • No puedes detener el contenedor de un nodo: es intencionado. container stop y delete rechazan los nodos de clúster; usa container cluster delete.
    Comparación con Docker Desktop y OrbStack

Docker Desktop tiene Kubernetes integrado con kubeadm (un nodo) o kind (varios nodos), y OrbStack tiene integrado un clúster de un solo nodo. container cluster ejecuta kubeadm sobre imágenes kindest/node, cada nodo en su propia VM, con clústeres de varios nodos y el almacén de imágenes compartido. Consulta la comparativa completa.

Clústeres desde agentes de IA

El servidor MCP de Gantry tiene list_clusters, create_cluster y delete_cluster, así que un agente como Claude Code puede crear un clúster temporal para una prueba y eliminarlo después.

Añadir el servidor MCP de Gantry
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Preguntas y respuestas

¿Apple container es compatible con Kubernetes?

Sí. La CLI container crea clústeres de Kubernetes cuyos nodos se ejecutan como contenedores: container cluster en las CLI 1.6.1 y 1.7, container k8s en las CLI 1.5.0 a 1.6.0. Gantry le pone una GUI.

¿Gantry es compatible con container cluster?

Sí. Gantry lista, crea y elimina clústeres en hosts apple/container, muestra sus nodos, escribe el kubeconfig y abre el clúster en su navegador de Kubernetes. En la CLI 1.7 también define el tamaño de los workers y activa el almacén de imágenes compartido. Usa cluster o k8s según tu versión de la CLI.

¿Cómo uso kubectl con un clúster de apple/container?

Cuando la CLI crea un clúster, añade a ~/.kube/config un contexto de kubeconfig con el nombre del clúster. Ejecuta kubectl --context <name> get nodes. Para tenerlo en un archivo aparte, usa Escribir kubeconfig en Gantry; la ruta predeterminada es ~/.kube/<name>.kubeconfig.

¿Cómo meto una imagen local en el clúster sin un registro?

En la CLI 1.7, crea el clúster con Usar imágenes locales (--shared-image-store). Los pods ejecutan entonces por su nombre las imágenes que compilas o descargas con container. En las CLI 1.5 y 1.6, haz clic derecho en la imagen en Imágenes y elige Cargar en el clúster; Gantry ejecuta container cluster load-image. La CLI 1.7 eliminó load-image.

¿Puedo crear un clúster con varios nodos?

Sí. Indica el número de workers en la hoja de creación; los workers requieren la CLI 1.6.0 o posterior. En la CLI 1.7 también defines la CPU y la memoria de los workers por separado del plano de control.

¿Puedo usar mi propia CNI, como Calico o Cilium?

Sí. Elige Manifiesto personalizado y selecciona el archivo del manifiesto, o elige Ninguno y aplica tú una CNI cuando el clúster haya arrancado. Los nodos siguen en NotReady hasta que hay una CNI en ejecución. Ninguno requiere la CLI 1.6.0 o posterior. La CNI predeterminada es el manifiesto de kindnet incluido.

¿Por qué Gantry dice que los servicios de clúster no están disponibles?

Los servicios de container no respondieron a un comando de clúster. Si tu CLI es una versión de Homebrew sin los servicios de clúster, Gantry lo indica y enlaza al instalador firmado de la página de versiones de apple/container. En otro caso, ofrece Reiniciar servicios.

¿Necesito kubectl para usar el clúster en Gantry?

De momento, sí: el navegador de Kubernetes de Gantry ejecuta kubectl. Si no está instalado, el navegador muestra el comando brew install kubectl y puede ejecutarlo por ti.

¿Puedo ejecutar Kubernetes en un Mac sin Docker?

Sí. La CLI container de Apple crea por sí misma clústeres de Kubernetes con container cluster create. Cada nodo se ejecuta como una VM ligera, y no necesitas Docker, Docker Desktop, kind ni minikube.

¿Cuántos nodos puede tener un container cluster?

Un plano de control y tantos workers como permitan la CPU y la memoria de tu Mac. Defínelos con --workers; en la CLI 1.7, cada grupo de workers puede tener su propia CPU y memoria.

¿Qué versión de Kubernetes usa container cluster?

La CLI 1.7.1 usa de forma predeterminada la imagen de nodo kindest/node:v1.35.5. Elige otra versión con --node-image, por ejemplo docker.io/kindest/node:v1.34.11. Gantry muestra la versión en el resumen del clúster.
