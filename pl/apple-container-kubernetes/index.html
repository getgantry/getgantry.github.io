Gantry/Kubernetes na apple/container

Kubernetes na Apple container

apple/container potrafi uruchomić klaster Kubernetes, którego węzły są kontenerami na Twoim Macu. Gantry to dla niego GUI: utwórz klaster, obserwuj, jak startują węzły, uruchamiaj w nim lokalne obrazy i przeglądaj jego pody, logi i usługi – bez długich poleceń container cluster.

W skrócie. Na hoście apple/container sekcja Klastry w Gantry tworzy i usuwa klastry Kubernetes poleceniem container cluster (CLI 1.6.1 i 1.7) lub container k8s (CLI od 1.5.0 do 1.6.0). W CLI 1.7.1 ustawia rozmiar węzłów roboczych niezależnie od warstwy sterowania i włącza współdzielony magazyn obrazów. Sekcja Kubernetes służy do przeglądania klastra: pody, logi, powłoka, przekierowania portów, skalowanie i Zastosuj YAML.

Wymagania

  • Mac z Apple silicon, macOS 26 i Gantry (brew install --cask getgantry/tap/gantry).
  • CLI container 1.5.0 lub nowsze; zalecane 1.7.1. Węzły robocze i CNI Brak wymagają 1.6.0 lub nowszego. Rozmiary węzłów roboczych i współdzielony magazyn obrazów wymagają 1.7.0 lub nowszego. Użyj podpisanego pakietu instalacyjnego: wersja 1.7.1 z Homebrew nie ma usług klastra.
  • kubectl dla przeglądarki Kubernetes i terminala. Gantry może go zainstalować przez Homebrew.

Tworzenie klastra

  1. Wybierz host apple/container i otwórz Klastry na pasku bocznym.
  2. Rozpocznij tworzenie nowego klastra i wypełnij opcje opisane poniżej.
  3. Utwórz klaster. Lista pokazuje nowy klaster z postępem na żywo. Anuluj przerywa tworzenie i usuwa już utworzone węzły.
OpcjaFlaga CLIUwagi
Nazwa--nameTakże nazwa kontekstu kubeconfig

Procesory i pamięć węzłów roboczych--workers count=N,cpus=C,memory=MCLI 1.7+. Przed 1.7 --cpus i --memory ustawiają każdy węzeł

To samo polecenie w CLI:

Powłoka
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Węzły i szczegóły klastra

Lista klastrów ma jeden wiersz dla każdego klastra. Widok szczegółów zawiera Przegląd (kontekst kubectl, serwer API, wersja Kubernetes, magazyn obrazów, węzły robocze i ich zasoby, sieć węzłów), tabelę Węzły i kartę Inspekcja z surowymi danymi węzłów. Na pasku narzędzi jest Przeglądaj zasoby, a w menu Więcej Zapisz kubeconfig, Kopiuj polecenie kontekstu kubectl i Usuń.

Węzły klastra są kontenerami, ale należą do container cluster. Gantry blokuje dla węzła uruchamianie, zatrzymywanie, ponowne uruchamianie, usuwanie i zmianę nazwy i wyjaśnia dlaczego, a Uruchom wszystkie i Zatrzymaj wszystkie pomijają węzły. W CLI 1.7 samo CLI ukrywa też węzły w container list. Klastry utworzone w CLI 1.6 lub starszym nie pojawiają się na liście w 1.7; usuń je poleceniem container cluster delete --name <name>.

Przeglądanie klastra

Kliknij Przeglądaj zasoby przy działającym klastrze albo otwórz Kubernetes na pasku bocznym. Sekcja nie wymaga hosta i wyświetla każdy kontekst kubeconfig; konteksty klastrów apple/container są na początku. Wybierz przestrzeń nazw lub wszystkie przestrzenie nazw, a potem rodzaj zasobu: pody, deploymenty, StatefulSety, DaemonSety, usługi, ingressy, ConfigMapy, sekrety, węzły lub zdarzenia.

  • Pody: logi ze śledzeniem, końcówką i poprzednim kontenerem; powłoka w podzie; przekierowanie portu na 127.0.0.1.
  • Workloady: skalowanie deploymentów i StatefulSetów; restart wdrożenia.
  • Sekrety: wartości są zamaskowane na liście i w YAML, dopóki nie klikniesz Pokaż.
  • Zastosuj YAML: wklej manifest lub otwórz plik; błędy pojawiają się w arkuszu.

Przeglądarka uruchamia kubectl. Jeśli Gantry go nie znajdzie, sekcja pokazuje brew install kubectl z przyciskiem, który je uruchamia.

Podłączenie kubectl

Tworząc klaster, CLI dodaje do ~/.kube/config kontekst o nazwie klastra. Użyj w Gantry Kopiuj polecenie kontekstu kubectl albo wpisz je ręcznie:

Powłoka
kubectl --context dev get nodes

Aby trzymać klaster w osobnym pliku, użyj Zapisz kubeconfig. Gantry uruchamia container cluster write-config; domyślna ścieżka to ~/.kube/<name>.kubeconfig.

Lokalne obrazy w klastrze

W CLI 1.7 włącz Używaj lokalnych obrazów przy tworzeniu klastra. Opcja dodaje --shared-image-store, więc węzły mogą uruchomić po nazwie każdy obraz, który budujesz lub pobierasz poleceniem container, bez rejestru. Ustawienia nie można zmienić po utworzeniu klastra. Po ponownym zbudowaniu tagu użyj imagePullPolicy: Always lub nowego tagu. Pody uprzywilejowane mogą odczytać każdy obraz z Twojego lokalnego magazynu, więc używaj tej opcji tylko do pracy lokalnej.

Powłoka
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

W CLI 1.5 i 1.6 kliknij obraz prawym przyciskiem w sekcji Obrazy i wybierz Wczytaj do klastra. Gantry uruchamia container cluster load-image, które kopiuje obraz do containerd każdego węzła. CLI 1.7 usunęło to polecenie, więc Gantry ukrywa tam tę akcję.

Powłoka
container cluster load-image --name dev myapp:dev

Gdy usługi klastra nie odpowiadają

Jeśli polecenie klastra kończy się błędem cluster service unavailable, Gantry sprawdza, jak zainstalowano CLI. Wersja z Homebrew bez wtyczek klastra dostaje komunikat, że brakuje w niej usług klastra, oraz link Pobierz instalator… do podpisanego pakietu. W pozostałych przypadkach Gantry proponuje Uruchom ponownie usługi….

Wybór CNI

Domyślnie używany jest wbudowany manifest kindnet. Wybierz Własny manifest, aby zainstalować własny CNI z pliku, na przykład Calico lub Cilium. Wybierz Brak, aby zainstalować CNI samodzielnie później; do tego czasu węzły pozostają w stanie NotReady.

Kubernetes na Macu z Apple container

Narzędzie container od Apple tworzy lokalny klaster Kubernetes jednym poleceniem. Każdy węzeł to lekka maszyna wirtualna na Twoim Macu. Ten przewodnik prowadzi od pustego Maca do działającego deploymentu, najpierw w terminalu, a potem w Gantry.

Czego potrzebujesz

  • Mac z Apple silicon i macOS 26 lub nowszym.
  • CLI container 1.7.1 z podpisanego pakietu .pkg ze strony wydań apple/container. Wersja 1.7.1 z Homebrew nie zawiera usług klastra, więc container cluster kończy się błędem cluster service unavailable.
  • Około 6 GB wolnej pamięci dla poniższego przykładu: trzy węzły po 2 GB.
  • kubectl, jeśli chcesz korzystać z klastra w terminalu (brew install kubectl).

Po instalacji pakietu uruchom usługi jeden raz:

Terminal
container system start
    Tworzenie klastra

To polecenie tworzy klaster o nazwie dev z jednym węzłem warstwy sterowania i dwoma węzłami roboczymi. Każdy węzeł dostaje 2 procesory i 2 GB pamięci:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M ustawia rozmiar grupy węzłów roboczych. Powtórz flagę dla grup o różnych rozmiarach. Bez --workers jeden węzeł jest jednocześnie warstwą sterowania i węzłem roboczym.
  • --cpus i --memory ustawiają rozmiar warstwy sterowania. Domyślnie to ćwierć procesorów i pamięci Twojego Maca, co najmniej 2 procesory i 2 GB.
  • --shared-image-store pozwala węzłom używać Twoich lokalnych obrazów (zobacz niżej). Nie da się tego zmienić później: usuń klaster i utwórz go ponownie.
  • --cni ./calico.yaml instaluje Twój własny CNI zamiast wbudowanego kindnet; --cni NONE nie instaluje żadnego.

CLI dodaje kontekst o nazwie dev do ~/.kube/config. Sprawdź węzły:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Lokalny obraz bez rejestru

Z --shared-image-store węzły mogą uruchomić każdy obraz z Twojego lokalnego magazynu obrazów container. Zbuduj obraz i użyj go po nazwie:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Uwaga
Po ponownym zbudowaniu tego samego tagu uruchom kubectl rollout restart z imagePullPolicy: Always albo użyj nowego tagu. Z IfNotPresent węzeł zachowuje kopię, którą już ma. Wszystko, co ma uprawnienia root na węźle, może odczytać każdy obraz z Twojego lokalnego magazynu, także obrazy prywatne, więc używaj współdzielonego magazynu tylko do pracy lokalnej.

W CLI 1.5 i 1.6 nie ma współdzielonego magazynu. Użyj tam container cluster load-image albo Wczytaj do klastra w Gantry. CLI 1.7 usunęło load-image.

    Otwórz aplikację w przeglądarce

Przekieruj lokalny port do deploymentu, a potem otwórz http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Zatrzymanie i usunięcie klastra
Terminal
container cluster delete --name dev

Jeśli węzeł warstwy sterowania się zatrzyma, na przykład po container system stop, usuń klaster i utwórz go ponownie. Klaster tymczasowy utwórz z --rm, aby jego węzły były usuwane po zatrzymaniu.

    Typowe problemy
  • cluster service unavailable: CLI pochodzi z Homebrew albo usługi nie działają. Zainstaluj podpisany pakiet lub uruchom ponownie usługi poleceniami container system stop i container system start. Gantry pokazuje tę samą radę w sekcji Klastry.
  • Na liście brakuje starego klastra: CLI 1.7 nie wyświetla klastrów utworzonych w 1.6 lub starszym. Usuń taki klaster poleceniem container cluster delete --name <name>.
  • Węzły pozostają w stanie NotReady: użyto --cni NONE. Zastosuj manifest CNI.
  • Nie można zatrzymać kontenera węzła: to celowe. container stop i delete odmawiają działania na węzłach klastra; użyj container cluster delete.
    Porównanie z Docker Desktop i OrbStack

Docker Desktop ma wbudowany Kubernetes z kubeadm (jeden węzeł) lub kind (kilka węzłów), a OrbStack ma wbudowany klaster z jednym węzłem. container cluster uruchamia kubeadm na obrazach kindest/node, każdy węzeł we własnej maszynie wirtualnej, z klastrami wielowęzłowymi i współdzielonym magazynem obrazów. Zobacz pełne porównanie.

Klastry z poziomu agentów AI

Serwer MCP Gantry ma narzędzia list_clusters, create_cluster i delete_cluster, więc agent, taki jak Claude Code, może utworzyć tymczasowy klaster do testu i potem go usunąć.

Pytania i odpowiedzi

Czy Apple container obsługuje Kubernetes?

Tak. CLI container tworzy klastry Kubernetes, których węzły działają jako kontenery: container cluster w CLI 1.6.1 i 1.7, container k8s w CLI od 1.5.0 do 1.6.0. Gantry dodaje do tego GUI.

Czy Gantry obsługuje container cluster?

Tak. Gantry wyświetla, tworzy i usuwa klastry na hostach apple/container, pokazuje ich węzły, zapisuje kubeconfig i otwiera klaster w swojej przeglądarce Kubernetes. W CLI 1.7 ustawia też rozmiar węzłów roboczych i włącza współdzielony magazyn obrazów. Używa cluster lub k8s zależnie od wersji CLI.

Jak używać kubectl z klastrem apple/container?

Gdy CLI tworzy klaster, dodaje do ~/.kube/config kontekst kubeconfig o nazwie klastra. Uruchom kubectl --context <name> get nodes. Aby trzymać klaster w osobnym pliku, użyj w Gantry Zapisz kubeconfig; domyślna ścieżka to ~/.kube/<name>.kubeconfig.

Jak wczytać lokalny obraz do klastra bez rejestru?

W CLI 1.7 utwórz klaster z opcją Używaj lokalnych obrazów (--shared-image-store). Pody uruchamiają wtedy obrazy, które budujesz lub pobierasz poleceniem container, po nazwie. W CLI 1.5 i 1.6 kliknij obraz prawym przyciskiem w sekcji Obrazy i wybierz Wczytaj do klastra; Gantry uruchamia container cluster load-image. CLI 1.7 usunęło load-image.

Czy można utworzyć klaster z wieloma węzłami?

Tak. Ustaw liczbę węzłów roboczych w arkuszu tworzenia; węzły robocze wymagają CLI 1.6.0 lub nowszego. W CLI 1.7 ustawiasz też procesory i pamięć węzłów roboczych niezależnie od warstwy sterowania.

Czy mogę użyć własnego CNI, np. Calico lub Cilium?

Tak. Wybierz Własny manifest i wskaż plik manifestu albo wybierz Brak i zainstaluj CNI samodzielnie po uruchomieniu klastra. Węzły pozostają w stanie NotReady, dopóki CNI nie działa. Brak wymaga CLI 1.6.0 lub nowszego. Domyślny CNI to wbudowany manifest kindnet.

Dlaczego Gantry podaje, że usługi klastra są niedostępne?

Usługi container nie odpowiedziały na polecenie klastra. Jeśli Twoje CLI to wersja z Homebrew bez usług klastra, Gantry o tym informuje i podaje link do podpisanego instalatora na stronie wydań apple/container. W przeciwnym razie proponuje Uruchom ponownie usługi.

Czy do pracy z klastrem w Gantry potrzebuję kubectl?

Na razie tak: przeglądarka Kubernetes w Gantry uruchamia kubectl. Jeśli go nie ma, przeglądarka pokazuje polecenie brew install kubectl i może je uruchomić za Ciebie.

Czy mogę uruchomić Kubernetes na Macu bez Dockera?

Tak. CLI container od Apple samo tworzy klastry Kubernetes poleceniem container cluster create. Każdy węzeł działa jako lekka maszyna wirtualna i nie potrzebujesz Dockera, Docker Desktop, kind ani minikube.

Ile węzłów może mieć container cluster?

Jedną warstwę sterowania i tyle węzłów roboczych, na ile starczy procesorów i pamięci Twojego Maca. Ustaw je flagą --workers; w CLI 1.7 każda grupa węzłów roboczych może mieć własne procesory i pamięć.

Której wersji Kubernetes używa container cluster?

CLI 1.7.1 domyślnie używa obrazu węzła kindest/node:v1.35.5. Inną wersję wybierzesz flagą --node-image, na przykład docker.io/kindest/node:v1.34.11. Gantry pokazuje wersję w przeglądzie klastra.
