Gantry/Kubernetes på apple/container

Kubernetes på Apple container

apple/container kan köra ett Kubernetes-kluster vars noder är containrar på din Mac. Gantry är ett GUI för det: skapa ett kluster, se noderna starta, kör dina lokala images i det och bläddra bland poddar, loggar och services, utan långa container cluster-kommandorader.

Kort sagt. På en apple/container-värd skapar och raderar Gantrys avsnitt Kluster Kubernetes-kluster med container cluster (CLI 1.6.1 och 1.7) eller container k8s (CLI 1.5.0 till 1.6.0). På CLI 1.7.1 anger det storlek för dina workers separat från kontrollplanet och slår på det delade image-lagret. Avsnittet Kubernetes bläddrar i klustret: poddar, loggar, skal, portvidarebefordringar, skalning och Verkställ YAML.

Krav

  • En Mac med Apple-chip, macOS 26 och Gantry (brew install --cask getgantry/tap/gantry).
  • container-CLI 1.5.0 eller senare; 1.7.1 rekommenderas. Workers och CNI:n Ingen kräver 1.6.0 eller senare. Worker-storlekar och det delade image-lagret kräver 1.7.0 eller senare. Använd det signerade installationspaketet: Homebrew-bygget av 1.7.1 har inga klustertjänster.
  • kubectl för Kubernetes-utforskaren och terminalen. Gantry kan installera det med Homebrew.

Skapa ett kluster

  1. Välj din apple/container-värd och öppna Kluster i sidofältet.
  2. Starta ett nytt kluster och fyll i alternativen nedan.
  3. Skapa det. Listan visar det nya klustret och förloppet live. Avbryt stoppar skapandet och raderar de noder som redan har skapats.
AlternativCLI-flaggaKommentar
Namn--nameÄven namnet på kubeconfig-kontexten
Workers--workersAntal worker-noder. CLI 1.6.0+
CPU:er och minne för workers--workers count=N,cpus=C,memory=MCLI 1.7+. Före 1.7 anger --cpus och --memory värdet för varje nod
CPU:er--cpusKontrollplanet (CLI 1.7+), eller varje nod (före 1.7)
Minne--memoryKontrollplanet (CLI 1.7+), eller varje nod (före 1.7), till exempel 4G
Använd lokala images--shared-image-storeCLI 1.7+. Noderna kör images från ditt lokala image-lager
Nodimage--node-imageTomt behåller CLI:ets standard
CNI--cniStandard (medföljande kindnet), Ingen (NONE, CLI 1.6.0+) eller sökväg till ett anpassat manifest

Samma kommando i CLI:et:

Skal
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Noder och klusterdetaljer

Klusterlistan visar en rad per kluster. Detaljvyn har en Översikt (kubectl-kontext, API-server, Kubernetes-version, image-lager, workers och deras resurser, nodnätverk), en tabell Noder och Granska för rådata om noderna. Verktygsfältet har Bläddra bland resurser, och menyn Mer har Skriv kubeconfig, Kopiera kubectl-kontextkommando och Radera.

Klusternoder är containrar, men de ägs av container cluster. Gantry stänger av start, stopp, omstart, borttagning och namnbyte för en nod och förklarar varför, och Starta alla och Stoppa alla hoppar över noder. På CLI 1.7 döljer CLI:et också noder i container list. Kluster som skapats med CLI 1.6 eller tidigare visas inte i listan i 1.7; ta bort dem med container cluster delete --name <name>.

Bläddra i klustret

Klicka på Bläddra bland resurser för ett kluster som körs, eller öppna Kubernetes i sidofältet. Avsnittet behöver ingen värd och listar varje kubeconfig-kontext; kontexterna för apple/container-kluster visas först. Välj en namnrymd eller alla namnrymder, och sedan en sort: poddar, deployments, stateful sets, daemon sets, services, ingresses, config maps, secrets, noder eller händelser.

  • Poddar: loggar med följ, tail och föregående container; ett skal i podden; portvidarebefordring till 127.0.0.1.
  • Arbetslaster: skala deployments och stateful sets; starta om en utrullning.
  • Secrets: värden är maskerade i listan och i YAML tills du klickar på Visa.
  • Verkställ YAML: klistra in ett manifest eller öppna en fil; fel visas i arket.

Utforskaren kör kubectl. Om Gantry inte hittar det visar avsnittet brew install kubectl med en knapp som kör kommandot.

Anslut kubectl

CLI:et lägger till en kontext med klustrets namn i ~/.kube/config när det skapar klustret. Använd Kopiera kubectl-kontextkommando i Gantry, eller skriv det själv:

Skal
kubectl --context dev get nodes

Om du vill ha klustret i en egen fil använder du Skriv kubeconfig. Gantry kör container cluster write-config; standardsökvägen är ~/.kube/<name>.kubeconfig.

Använd lokala images i klustret

På CLI 1.7 slår du på Använd lokala images när du skapar klustret. Det lägger till --shared-image-store, så att noderna kan köra varje image som du bygger eller hämtar med container, via namn, utan register. Inställningen bestäms när klustret skapas. När du har byggt om en tagg använder du imagePullPolicy: Always eller en ny tagg. Privilegierade poddar kan läsa varje image i ditt lokala lager, så använd det här bara för lokal utveckling.

Skal
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

På CLI 1.5 och 1.6 högerklickar du på imagen i Images och väljer Läs in i kluster. Gantry kör container cluster load-image, som kopierar imagen till containerd på varje nod. CLI 1.7 tog bort det här kommandot, så där döljer Gantry åtgärden.

Skal
container cluster load-image --name dev myapp:dev

När klustertjänsterna inte svarar

Om ett klusterkommando misslyckas med cluster service unavailable kontrollerar Gantry hur CLI:et är installerat. Ett Homebrew-bygge utan klustertilläggen får meddelandet att bygget saknar klustertjänsterna och en länk Hämta installationsprogram… till det signerade paketet. I andra fall erbjuder Gantry Starta om tjänster….

Välj en CNI

Standard är det medföljande kindnet-manifestet. Välj Anpassat manifest för att installera en egen CNI, till exempel Calico eller Cilium, från en fil. Välj Ingen om du vill installera en CNI själv senare; tills dess förblir noderna NotReady.

Kör Kubernetes på en Mac med Apple container

Apples container-verktyg kan skapa ett lokalt Kubernetes-kluster med ett enda kommando. Varje nod är en lätt virtuell maskin på din Mac. Den här guiden går från en tom Mac till en deployment som körs, först i terminalen och sedan i Gantry.

Det här behöver du

  • En Mac med Apple-chip och macOS 26 eller senare.
  • container-CLI 1.7.1 från den signerade .pkg-filen på versionssidan för apple/container. Homebrew-bygget av 1.7.1 saknar klustertjänsterna, så container cluster misslyckas med cluster service unavailable.
  • Cirka 6 GB ledigt minne för exemplet nedan: tre noder med 2 GB vardera.
  • kubectl om du vill använda klustret från terminalen (brew install kubectl).

Starta tjänsterna en gång när du har installerat paketet:

Terminal
container system start
    Skapa klustret

Det här kommandot skapar ett kluster med namnet dev med en kontrollplansnod och två workers. Varje nod får 2 CPU:er och 2 GB minne:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M anger storleken för en grupp workers. Upprepa det för grupper av olika storlek. Utan --workers är en enda nod både kontrollplan och worker.
  • --cpus och --memory anger storleken för kontrollplanet. Standard är en fjärdedel av din Macs CPU:er och minne, minst 2 CPU:er och 2 GB.
  • --shared-image-store låter noderna använda dina lokala images (se nedan). Du kan inte ändra det senare: radera klustret och skapa det igen.
  • --cni ./calico.yaml installerar din egen CNI i stället för den medföljande kindnet; --cni NONE installerar ingen.

CLI:et lägger till en kontext med namnet dev i ~/.kube/config. Kontrollera noderna:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Kör en lokal image utan register

Med --shared-image-store kan noderna köra vilken image som helst i ditt lokala image-lager för container. Bygg en image och använd den via namn:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Anmärkning
När du har byggt om samma tagg kör du kubectl rollout restart med imagePullPolicy: Always, eller använder en ny tagg. Med IfNotPresent behåller en nod den kopia den redan har. Allt med root på en nod kan läsa varje image i ditt lokala lager, även privata images, så använd det delade lagret bara för lokal utveckling.

På CLI 1.5 och 1.6 finns inget delat lager. Använd container cluster load-image där, eller Läs in i kluster i Gantry. CLI 1.7 tog bort load-image.

    Öppna appen i en webbläsare

Vidarebefordra en lokal port till din deployment och öppna sedan http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Stoppa och radera klustret
Terminal
container cluster delete --name dev

Om kontrollplansnoden stoppas, till exempel efter container system stop, raderar du klustret och skapar det igen. Skapa ett tillfälligt kluster med --rm så tas noderna bort när de stoppas.

    Vanliga problem
  • cluster service unavailable: CLI:et är Homebrew-bygget, eller tjänsterna körs inte. Installera det signerade paketet, eller starta om tjänsterna med container system stop och container system start. Gantry visar samma råd i Kluster.
  • Ett gammalt kluster saknas i listan: CLI 1.7 listar inte kluster som skapats med 1.6 eller tidigare. Ta bort ett sådant med container cluster delete --name <name>.
  • Noderna förblir NotReady: du använde --cni NONE. Verkställ ett CNI-manifest.
  • Du kan inte stoppa en nodcontainer: det är avsiktligt. container stop och delete vägrar för klusternoder; använd container cluster delete.
    Så här står det sig mot Docker Desktop och OrbStack

Docker Desktop har inbyggd Kubernetes med kubeadm (en nod) eller kind (flera noder), och OrbStack har ett inbyggt kluster med en nod. container cluster kör kubeadm på kindest/node-images, varje nod i en egen VM, med kluster med flera noder och det delade image-lagret. Se den fullständiga jämförelsen.

Kluster från AI-agenter

Gantrys MCP-server har list_clusters, create_cluster och delete_cluster, så en agent som Claude Code kan skapa ett tillfälligt kluster för ett test och ta bort det efteråt.

Lägg till Gantrys MCP-server
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

En genomgång steg för steg från terminalen finns i Kör Kubernetes på en Mac med Apple container. Läs guiden till apple/container för varje container-kommando och dess funktion i Gantry, eller se hur Gantry står sig mot Docker Desktop, OrbStack och Podman Desktop.

Frågor och svar

Stöder Apple container Kubernetes?

Ja. container-CLI:et skapar Kubernetes-kluster vars noder körs som containrar: container cluster i CLI 1.6.1 och 1.7, container k8s i CLI 1.5.0 till 1.6.0. Gantry ger det ett GUI.

Stöder Gantry container cluster?

Ja. Gantry listar, skapar och raderar kluster på apple/container-värdar, visar deras noder, skriver kubeconfig och öppnar klustret i sin Kubernetes-utforskare. På CLI 1.7 anger den också storlek för dina workers och slår på det delade image-lagret. Den använder cluster eller k8s beroende på din CLI-version.

Hur använder jag kubectl med ett kluster i apple/container?

När CLI:et skapar ett kluster lägger det till en kubeconfig-kontext med klustrets namn i ~/.kube/config. Kör kubectl --context <name> get nodes. Om du vill ha en separat fil använder du Skriv kubeconfig i Gantry; standardsökvägen är ~/.kube/<name>.kubeconfig.

Hur får jag in en lokal image i klustret utan register?

På CLI 1.7 skapar du klustret med Använd lokala images (--shared-image-store). Poddarna kör då de images du bygger eller hämtar med container, via namn. På CLI 1.5 och 1.6 högerklickar du på imagen under Images och väljer Läs in i kluster; Gantry kör container cluster load-image. CLI 1.7 tog bort load-image.

Kan jag skapa ett kluster med flera noder?

Ja. Ange antalet workers i arket för att skapa klustret; workers kräver CLI 1.6.0 eller senare. På CLI 1.7 anger du också CPU:er och minne för dina workers separat från kontrollplanet.

Kan jag använda en egen CNI som Calico eller Cilium?

Ja. Välj Anpassat manifest och välj manifestfilen, eller välj Ingen och installera en CNI själv när klustret har startat. Noderna förblir NotReady tills en CNI körs. Ingen kräver CLI 1.6.0 eller senare. Standard-CNI:n är det medföljande kindnet-manifestet.

Varför säger Gantry att klustertjänsterna inte är tillgängliga?

container-tjänsterna svarade inte på ett klusterkommando. Om ditt CLI är ett Homebrew-bygge utan klustertjänsterna säger Gantry det och länkar till det signerade installationsprogrammet på versionssidan för apple/container. Annars erbjuder den Starta om tjänster.

Behöver jag kubectl för att använda klustret i Gantry?

Just nu, ja: Gantrys Kubernetes-utforskare kör kubectl. Om det inte är installerat visar utforskaren kommandot brew install kubectl och kan köra det åt dig.

Kan jag köra Kubernetes på en Mac utan Docker?

Ja. Apples container-CLI skapar Kubernetes-kluster själv med container cluster create. Varje nod körs som en lätt VM, och du behöver inte Docker, Docker Desktop, kind eller minikube.

Hur många noder kan ett container cluster ha?

Ett kontrollplan och så många workers som din Mac har CPU:er och minne till. Ange dem med --workers; på CLI 1.7 kan varje grupp workers ha egna CPU:er och eget minne.

Vilken Kubernetes-version använder container cluster?

CLI 1.7.1 använder nodimagen kindest/node:v1.35.5 som standard. Välj en annan version med --node-image, till exempel docker.io/kindest/node:v1.34.11. Gantry visar versionen i klusteröversikten.
