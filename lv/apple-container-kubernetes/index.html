Gantry/Kubernetes apple/container vidē

Kubernetes ar Apple container

apple/container var palaist Kubernetes klasteri, kura mezgli ir konteineri jūsu Mac datorā. Gantry tam ir grafiskā saskarne: izveidojiet klasteri, vērojiet, kā startē mezgli, palaidiet tajā savus lokālos attēlus un pārlūkojiet tā podus, žurnālus un pakalpojumus bez garām container cluster komandrindām.

Īsumā. apple/container resursdatorā Gantry sadaļa Klasteri izveido un dzēš Kubernetes klasterus ar container cluster (CLI 1.6.1 un 1.7) vai container k8s (CLI no 1.5.0 līdz 1.6.0). CLI 1.7.1 versijā tā iestata darba mezglu izmēru atsevišķi no vadības plaknes un ieslēdz kopīgo attēlu krātuvi. Sadaļa Kubernetes pārlūko klasteri: podi, žurnāli, čaula, portu pārsūtīšana, mērogošana un YAML lietošana.

Prasības

  • Mac dators ar Apple silicon, macOS 26 un Gantry (brew install --cask getgantry/tap/gantry).
  • container CLI 1.5.0 vai jaunāks; ieteicams 1.7.1. Darba mezgliem un CNI opcijai Nav nepieciešams 1.6.0 vai jaunāks. Darba mezglu izmēriem un kopīgajai attēlu krātuvei nepieciešams 1.7.0 vai jaunāks. Izmantojiet parakstīto instalācijas pakotni: 1.7.1 Homebrew versijā nav klastera pakalpojumu.
  • Gantry Kubernetes pārlūkam nekas cits nav vajadzīgs. kubectl – tikai tad, ja vēlaties izmantot klasteri arī no termināļa.

Klastera izveide

  1. Atlasiet savu apple/container resursdatoru un sānjoslā atveriet Klasteri.
  2. Sāciet jauna klastera izveidi un aizpildiet tālāk norādītās opcijas.
  3. Izveidojiet to. Sarakstā tiek rādīts jaunais klasteris un norise reāllaikā. Atcelt pārtrauc izveidi un dzēš jau izveidotos mezglus.
OpcijaCLI karodziņšPiezīmes

Darba mezgli--workersDarba mezglu skaits. CLI 1.6.0+
Darba mezglu CPU un atmiņa--workers count=N,cpus=C,memory=MCLI 1.7+. Pirms 1.7 --cpus un --memory attiecas uz visiem mezgliem

Tā pati komanda CLI:

Čaula
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Mezgli un klastera informācija

Klasteru sarakstā katram klasterim ir viena rinda. Detalizētajā skatā ir Pārskats (kubectl konteksts, API serveris, Kubernetes versija, attēlu krātuve, darba mezgli un to resursi, mezglu tīkls), tabula Mezgli un Pārbaudīt neapstrādātiem mezglu datiem. Rīkjoslā ir Pārlūkot resursus, bet izvēlnē „Vairāk” – Ierakstīt kubeconfig, Kopēt kubectl konteksta komandu un Dzēst.

Klastera mezgli ir konteineri, bet tos pārvalda container cluster. Gantry mezglam atspējo startēšanu, apturēšanu, restartēšanu, noņemšanu un pārdēvēšanu un paskaidro, kāpēc, bet „Startēt visus” un „Apturēt visus” izlaiž mezglus. CLI 1.7 versijā CLI arī paslēpj mezglus no container list. Klasteri, kas izveidoti ar CLI 1.6 vai vecāku, 1.7 sarakstā netiek rādīti; noņemiet tos ar container cluster delete --name <name>.

Klastera pārlūkošana

Klasterim, kas darbojas, noklikšķiniet uz Pārlūkot resursus vai sānjoslā atveriet Kubernetes. Sadaļai nav vajadzīgs resursdators, un tā rāda katru kubeconfig kontekstu; apple/container klasteru konteksti ir pirmie. Izvēlieties nosaukumtelpu vai visas nosaukumtelpas un pēc tam veidu: podi, Deployments, StatefulSets, DaemonSets, pakalpojumi, Ingresses, ConfigMaps, noslēpumi, mezgli vai notikumi.

  • Podi: žurnāli ar sekošanu, pēdējām rindām un iepriekšējo konteineru; čaula podā; porta pārsūtīšana uz 127.0.0.1.
  • Darba slodzes: Deployments un StatefulSets mērogošana; izvēršanas restartēšana.
  • Noslēpumi: vērtības sarakstā un YAML ir paslēptas, līdz noklikšķināt uz „Atklāt”.
  • Lietot YAML: ielīmējiet manifestu vai atveriet failu; kļūdas tiek rādītas logā.

Gantry pati sazinās ar Kubernetes API, izmantojot jūsu kubeconfig akreditācijas datus. Jums nav vajadzīgs ne kubectl, ne cits rīks: klasteri, kas izveidots ar container cluster create, var pārlūkot uzreiz.

kubectl pieslēgšana

Izveidojot klasteri, CLI failā ~/.kube/config pievieno kontekstu ar klastera nosaukumu. Lietotnē Gantry izmantojiet Kopēt kubectl konteksta komandu vai ierakstiet to paši:

Čaula
kubectl --context dev get nodes

Lai glabātu klasteri atsevišķā failā, izmantojiet Ierakstīt kubeconfig. Gantry izpilda container cluster write-config; noklusējuma ceļš ir ~/.kube/<name>.kubeconfig.

Lokālo attēlu izmantošana klasterī

CLI 1.7 versijā, veidojot klasteri, ieslēdziet Izmantot lokālos attēlus. Tas pievieno --shared-image-store, tāpēc mezgli pēc nosaukuma var palaist jebkuru attēlu, ko būvējat vai lejupielādējat ar container, bez reģistra. Iestatījumu nosaka izveides brīdī. Pēc taga atkārtotas būvēšanas izmantojiet imagePullPolicy: Always vai jaunu tagu. Priviliģētie podi var nolasīt katru attēlu jūsu lokālajā krātuvē, tāpēc izmantojiet to tikai lokālai izstrādei.

Čaula
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

CLI 1.5 un 1.6 versijā sadaļā Attēli ar peles labo pogu noklikšķiniet uz attēla un izvēlieties Ielādēt klasterī. Gantry izpilda container cluster load-image, kas nokopē attēlu uz katra mezgla containerd. CLI 1.7 versijā šī komanda ir noņemta, tāpēc tur Gantry šo darbību paslēpj.

Čaula
container cluster load-image --name dev myapp:dev

Ja klastera pakalpojumi neatbild

Ja klastera komanda beidzas ar kļūdu cluster service unavailable, Gantry pārbauda, kā CLI ir instalēts. Homebrew versijai bez klastera spraudņiem tiek parādīts ziņojums, ka šajā versijā nav klastera pakalpojumu, un saite Lejupielādēt instalētāju… uz parakstīto pakotni. Citos gadījumos Gantry piedāvā Restartēt pakalpojumus….

CNI izvēle

Noklusējums ir komplektā iekļautais kindnet manifests. Izvēlieties Pielāgots manifests, lai instalētu savu CNI, piemēram, Calico vai Cilium, no faila. Izvēlieties Nav, lai vēlāk paši instalētu CNI; līdz tam mezgli paliek stāvoklī NotReady.

Kubernetes palaišana Mac datorā ar Apple container

Apple rīks container var izveidot lokālu Kubernetes klasteri ar vienu komandu. Katrs mezgls ir viegla virtuālā mašīna jūsu Mac datorā. Šis ceļvedis ved no tukša Mac datora līdz darbojošam Deployment – vispirms terminālī un pēc tam lietotnē Gantry.

Kas jums vajadzīgs

  • Mac dators ar Apple silicon un macOS 26 vai jaunāku versiju.
  • container CLI 1.7.1 no parakstītās .pkg pakotnes apple/container laidienu lapā. 1.7.1 Homebrew versijā nav klastera pakalpojumu, tāpēc container cluster beidzas ar kļūdu cluster service unavailable.
  • Apmēram 6 GB brīvas atmiņas tālāk dotajam piemēram: trīs mezgli, katram 2 GB.
  • kubectl, ja vēlaties izmantot klasteri no termināļa (brew install kubectl).

Pēc pakotnes instalēšanas vienreiz startējiet pakalpojumus:

Terminālis
container system start
    Klastera izveide

Šī komanda izveido klasteri dev ar vienu vadības plaknes mezglu un diviem darba mezgliem. Katrs mezgls saņem 2 CPU un 2 GB atmiņas:

Terminālis
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M nosaka darba mezglu grupas izmēru. Atkārtojiet to grupām ar dažādiem izmēriem. Bez --workers viens mezgls ir gan vadības plakne, gan darba mezgls.
  • --cpus un --memory nosaka vadības plaknes izmēru. Noklusējums ir ceturtdaļa no jūsu Mac datora CPU un atmiņas, vismaz 2 CPU un 2 GB.
  • --shared-image-store ļauj mezgliem izmantot jūsu lokālos attēlus (skatiet tālāk). Vēlāk to mainīt nevar: dzēsiet klasteri un izveidojiet to no jauna.
  • --cni ./calico.yaml komplektā iekļautā kindnet vietā instalē jūsu CNI; --cni NONE neinstalē nevienu.

CLI failā ~/.kube/config pievieno kontekstu dev. Pārbaudiet mezglus:

Terminālis
container cluster list --nodes
kubectl --context dev get nodes
    Lokāla attēla palaišana bez reģistra

Ar --shared-image-store mezgli var palaist jebkuru attēlu no jūsu lokālās container attēlu krātuves. Uzbūvējiet attēlu un izmantojiet to pēc nosaukuma:

Terminālis
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Piezīme
Pēc tā paša taga atkārtotas būvēšanas izpildiet kubectl rollout restart ar imagePullPolicy: Always vai izmantojiet jaunu tagu. Ar IfNotPresent mezgls patur jau esošo kopiju. Viss, kam mezglā ir root tiesības, var nolasīt katru attēlu jūsu lokālajā krātuvē, arī privātos attēlus, tāpēc kopīgo krātuvi izmantojiet tikai lokālai izstrādei.

CLI 1.5 un 1.6 versijā kopīgās krātuves nav. Tur izmantojiet container cluster load-image vai lietotnē Gantry Ielādēt klasterī. CLI 1.7 versijā load-image ir noņemts.

    Lietotnes atvēršana pārlūkprogrammā

Pārsūtiet lokālo portu uz Deployment un pēc tam atveriet http://localhost:8080:

Terminālis
kubectl --context dev port-forward deployment/hello 8080:80
    Klastera apturēšana un dzēšana
Terminālis
container cluster delete --name dev

Ja vadības plaknes mezgls apstājas, piemēram, pēc container system stop, dzēsiet klasteri un izveidojiet to no jauna. Izveidojiet pagaidu klasteri ar --rm, lai tā mezgli tiktu noņemti, kad tie apstājas.

    Biežākās problēmas
  • cluster service unavailable: CLI ir Homebrew versija, vai pakalpojumi nedarbojas. Instalējiet parakstīto pakotni vai restartējiet pakalpojumus ar container system stop un container system start. Gantry sadaļā „Klasteri” sniedz to pašu padomu.
  • Sarakstā nav veca klastera: CLI 1.7 nerāda klasterus, kas izveidoti ar 1.6 vai vecāku versiju. Noņemiet tādu ar container cluster delete --name <name>.
  • Mezgli paliek stāvoklī NotReady: jūs izmantojāt --cni NONE. Lietojiet CNI manifestu.
  • Mezgla konteineru nevar apturēt: tā ir paredzēts. container stop un delete atsakās apstrādāt klastera mezglus; izmantojiet container cluster delete.
    Salīdzinājums ar Docker Desktop un OrbStack

Docker Desktop ir iebūvēts Kubernetes ar kubeadm (viens mezgls) vai kind (vairāki mezgli), un OrbStack ir iebūvēts klasteris ar vienu mezglu. container cluster palaiž kubeadm uz kindest/node attēliem, katru mezglu savā virtuālajā mašīnā, ar klasteriem no vairākiem mezgliem un kopīgu attēlu krātuvi. Skatiet pilno salīdzinājumu.

Klasteri no MI aģentiem

Gantry MCP serverim ir list_clusters, create_cluster un delete_cluster, tāpēc aģents, piemēram, Claude Code, var izveidot pagaidu klasteri testam un pēc tam to noņemt.

Pievienojiet Gantry MCP serveri
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Vairāk par apple/container

Ceļvedi soli pa solim no termināļa lasiet lapā Kubernetes palaišana Mac datorā ar Apple container. Lasiet apple/container ceļvedi par katru container komandu un tās Gantry iespēju vai skatiet, kā Gantry salīdzināma ar Docker Desktop, OrbStack un Podman Desktop.

Jautājumi un atbildes

Vai Apple container atbalsta Kubernetes?

Jā. container CLI izveido Kubernetes klasterus, kuru mezgli darbojas kā konteineri: container cluster CLI 1.6.1 un 1.7 versijā, container k8s CLI versijās no 1.5.0 līdz 1.6.0. Gantry tam piešķir grafisko saskarni.

Vai Gantry atbalsta container cluster?

Jā. Gantry rāda sarakstu, izveido un dzēš klasterus apple/container resursdatoros, rāda to mezglus, ieraksta kubeconfig un atver klasteri savā Kubernetes pārlūkā. CLI 1.7 versijā tā arī norāda darba mezglu izmēru un ieslēdz kopīgo attēlu krātuvi. Atbilstoši jūsu CLI versijai tā izmanto cluster vai k8s.

Kā izmantot kubectl ar apple/container klasteri?

Kad CLI izveido klasteri, tas failā ~/.kube/config pievieno kubeconfig kontekstu ar klastera nosaukumu. Izpildiet kubectl --context <name> get nodes. Lai glabātu atsevišķu failu, lietotnē Gantry izmantojiet Ierakstīt kubeconfig; noklusējuma ceļš ir ~/.kube/<name>.kubeconfig.

Kā ielādēt lokālu attēlu klasterī bez reģistra?

CLI 1.7 versijā izveidojiet klasteri ar Izmantot lokālos attēlus (--shared-image-store). Tad podi pēc nosaukuma palaiž attēlus, ko būvējat vai lejupielādējat ar container. CLI 1.5 un 1.6 versijā sadaļā „Attēli” ar peles labo pogu noklikšķiniet uz attēla un izvēlieties Ielādēt klasterī; Gantry izpilda container cluster load-image. CLI 1.7 versijā load-image ir noņemts.

Vai var izveidot klasteri ar vairākiem mezgliem?

Jā. Izveides logā norādiet darba mezglu skaitu; darba mezgliem nepieciešams CLI 1.6.0 vai jaunāks. CLI 1.7 versijā darba mezglu CPU un atmiņu varat iestatīt atsevišķi no vadības plaknes.

Vai var izmantot savu CNI, piemēram, Calico vai Cilium?

Jā. Izvēlieties Pielāgots manifests un atlasiet manifesta failu vai izvēlieties Nav un pēc klastera startēšanas paši instalējiet CNI. Kamēr CNI nedarbojas, mezgli paliek stāvoklī NotReady. Opcijai Nav nepieciešams CLI 1.6.0 vai jaunāks. Noklusējuma CNI ir komplektā iekļautais kindnet manifests.

Kāpēc Gantry ziņo, ka klastera pakalpojumi nav pieejami?

container pakalpojumi neatbildēja uz klastera komandu. Ja jūsu CLI ir Homebrew versija bez klastera pakalpojumiem, Gantry to pasaka un dod saiti uz parakstīto instalētāju apple/container laidienu lapā. Citos gadījumos tā piedāvā Restartēt pakalpojumus.

Vai klastera izmantošanai lietotnē Gantry ir vajadzīgs kubectl?

Nē. Gantry pati sazinās ar Kubernetes API: tā nolasa kubeconfig un pēc tam bez kubectl rāda resursus, straumē žurnālus, atver čaulu, pārsūta portus un lieto YAML. Klasteri, kas izveidots ar container cluster create, var pārlūkot uzreiz.

Vai Mac datorā var palaist Kubernetes bez Docker?

Jā. Apple container CLI pats izveido Kubernetes klasterus ar container cluster create. Katrs mezgls darbojas kā viegla virtuālā mašīna, un jums nav vajadzīgs ne Docker, ne Docker Desktop, ne kind, ne minikube.

Cik mezglu var būt container cluster klasterim?

Viena vadības plakne un tik darba mezglu, cik pietiek jūsu Mac datora CPU un atmiņas. Iestatiet tos ar --workers; CLI 1.7 versijā katrai darba mezglu grupai var būt savs CPU un atmiņas apjoms.

Kuru Kubernetes versiju izmanto container cluster?

CLI 1.7.1 pēc noklusējuma izmanto mezgla attēlu kindest/node:v1.35.5. Citu versiju izvēlieties ar --node-image, piemēram, docker.io/kindest/node:v1.34.11. Gantry rāda versiju klastera pārskatā.
