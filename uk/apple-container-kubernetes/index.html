Gantry/Kubernetes на apple/container

Kubernetes на Apple container

apple/container може запустити кластер Kubernetes, вузли якого — контейнери на вашому Mac. Gantry — GUI для цього: створіть кластер, стежте, як запускаються вузли, запускайте в ньому свої локальні образи й переглядайте його поди, журнали й сервіси без довгих команд container cluster.

Коротко. На хості apple/container розділ Кластери в Gantry створює й видаляє кластери Kubernetes командою container cluster (CLI 1.6.1 і 1.7) або container k8s (CLI від 1.5.0 до 1.6.0). У CLI 1.7.1 він задає розмір робочих вузлів окремо від вузла керування й вмикає спільне сховище образів. Розділ Kubernetes показує вміст кластера: поди, журнали, оболонку, переадресацію портів, масштабування й «Застосувати YAML».

Вимоги

  • Mac з Apple silicon, macOS 26 і Gantry (brew install --cask getgantry/tap/gantry).
  • CLI container версії 1.5.0 або новішої; рекомендовано 1.7.1. Для робочих вузлів і CNI Немає потрібна 1.6.0 або новіша. Для розмірів робочих вузлів і спільного сховища образів потрібна 1.7.0 або новіша. Використовуйте підписаний інсталяційний пакет: у збірці Homebrew версії 1.7.1 немає служб кластера.
  • kubectl для браузера Kubernetes і термінала. Gantry може інсталювати його через Homebrew.

Створення кластера

  1. Виберіть хост apple/container і відкрийте Кластери на боковій панелі.
  2. Почніть створення нового кластера й заповніть параметри нижче.
  3. Створіть його. Новий кластер з’явиться в списку, де в реальному часі видно перебіг створення. Скасувати зупиняє створення й видаляє вже створені вузли.
ПараметрПрапорець CLIПримітки

Та сама команда в CLI:

Термінал
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Вузли й відомості про кластер

У списку кластерів — один рядок на кластер. Детальний вигляд містить Огляд (контекст kubectl, API-сервер, версія Kubernetes, сховище образів, робочі вузли та їхні ресурси, мережа вузлів), таблицю Вузли і Перевірити з необробленими даними вузлів. На панелі інструментів є Переглянути ресурси, а в меню «Більше» — Записати kubeconfig, Скопіювати команду контексту kubectl і Видалити.

Вузли кластера — це контейнери, але ними керує container cluster. Gantry вимикає для вузла запуск, зупинку, перезапуск, вилучення й перейменування та пояснює чому, а «Запустити всі» і «Зупинити всі» пропускають вузли. У CLI 1.7 сам CLI також приховує вузли з container list. Кластери, створені в CLI 1.6 або раніше, не видно в списку 1.7; видаліть їх командою container cluster delete --name <name>.

Перегляд кластера

Натисніть Переглянути ресурси для запущеного кластера або відкрийте Kubernetes на боковій панелі. Розділу не потрібен хост, і він показує всі контексти kubeconfig; контексти кластерів apple/container ідуть першими. Виберіть простір імен або всі простори імен, потім тип об’єкта: поди, Deployments, StatefulSets, DaemonSets, сервіси, Ingress, ConfigMaps, секрети, вузли чи події.

  • Поди: журнали з відстеженням, останніми рядками й попереднім контейнером; оболонка в поді; переадресація порту на 127.0.0.1.
  • Робочі навантаження: масштабування Deployments і StatefulSets; перезапуск розгортання.
  • Секрети: значення приховано в списку та в YAML, доки ви не натиснете «Показати».
  • Застосувати YAML: вставте маніфест або відкрийте файл; помилки видно просто у вікні.

Браузер запускає kubectl. Якщо Gantry не знаходить його, розділ показує brew install kubectl і кнопку, яка виконує цю команду.

Під’єднання kubectl

Під час створення кластера CLI додає в ~/.kube/config контекст із назвою кластера. Натисніть Скопіювати команду контексту kubectl у Gantry або введіть команду самі:

Термінал
kubectl --context dev get nodes

Щоб зберігати кластер в окремому файлі, натисніть Записати kubeconfig. Gantry виконає container cluster write-config; типовий шлях — ~/.kube/<name>.kubeconfig.

Локальні образи в кластері

У CLI 1.7 увімкніть Використовувати локальні образи під час створення кластера. Це додає --shared-image-store, і вузли можуть запускати за назвою будь-який образ, який ви зібрали чи отримали за допомогою container, без реєстру. Параметр задається під час створення й потім не змінюється. Після перезбирання тегу використовуйте imagePullPolicy: Always або новий тег. Привілейовані поди можуть читати всі образи у вашому локальному сховищі, тому використовуйте це лише для локальної розробки.

Термінал
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

У CLI 1.5 і 1.6 клацніть образ у розділі Образи правою кнопкою й виберіть Імпортувати в кластер. Gantry виконає container cluster load-image: команда копіює образ у containerd кожного вузла. У CLI 1.7 цієї команди немає, тому там Gantry приховує цю дію.

Термінал
container cluster load-image --name dev myapp:dev

Якщо служби кластера не відповідають

Якщо команда кластера завершується помилкою cluster service unavailable, Gantry перевіряє, як інстальовано CLI. Для збірки Homebrew без плагінів кластера він повідомляє, що в збірці немає служб кластера, і дає посилання Завантажити інсталятор… на підписаний пакет. В інших випадках Gantry пропонує Перезапустити служби….

Вибір CNI

Типово використовується вбудований маніфест kindnet. Виберіть Власний маніфест, щоб інсталювати власний CNI з файлу, наприклад Calico або Cilium. Виберіть Немає, щоб інсталювати CNI згодом самостійно; доти вузли лишаються в стані NotReady.

Kubernetes на Mac з Apple container

Інструмент container від Apple створює локальний кластер Kubernetes однією командою. Кожен вузол — легка віртуальна машина на вашому Mac. Цей посібник веде від порожнього Mac до робочого Deployment: спочатку в терміналі, потім у Gantry.

Що потрібно

  • Mac з Apple silicon і macOS 26 або новішою.
  • CLI container 1.7.1 з підписаного пакета .pkg на сторінці релізів apple/container. У збірці Homebrew версії 1.7.1 немає служб кластера, тому container cluster завершується помилкою cluster service unavailable.
  • Близько 6 ГБ вільної пам’яті для прикладу нижче: три вузли по 2 ГБ.
  • kubectl, якщо ви хочете працювати з кластером із термінала (brew install kubectl).

Після інсталяції пакета один раз запустіть служби:

Термінал
container system start
    Створення кластера

Ця команда створює кластер dev з одним вузлом керування й двома робочими вузлами. Кожен вузол отримує 2 CPU і 2 ГБ пам’яті:

Термінал
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M задає групу робочих вузлів одного розміру. Для груп різного розміру повторіть прапорець. Без --workers один вузол є водночас вузлом керування й робочим.
  • --cpus і --memory задають розмір вузла керування. Типово це чверть CPU і пам’яті вашого Mac, але не менше ніж 2 CPU і 2 ГБ.
  • --shared-image-store дає вузлам змогу використовувати ваші локальні образи (див. нижче). Змінити це пізніше не можна: видаліть кластер і створіть його знову.
  • --cni ./calico.yaml інсталює ваш CNI замість вбудованого kindnet; --cni NONE не інсталює жодного.

CLI додає в ~/.kube/config контекст dev. Перевірте вузли:

Термінал
container cluster list --nodes
kubectl --context dev get nodes
    Локальний образ без реєстру

З --shared-image-store вузли можуть запускати будь-який образ із вашого локального сховища образів container. Зберіть образ і використовуйте його за назвою:

Термінал
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Примітка
Після перезбирання того самого тегу виконайте kubectl rollout restart з imagePullPolicy: Always або використайте новий тег. З IfNotPresent вузол залишає копію, яку вже має. Будь-що з правами root на вузлі може читати всі образи вашого локального сховища, зокрема приватні, тому використовуйте спільне сховище лише для локальної розробки.

У CLI 1.5 і 1.6 спільного сховища немає. Там використовуйте container cluster load-image або Імпортувати в кластер у Gantry. У CLI 1.7 команди load-image більше немає.

    Відкрийте застосунок у браузері

Переадресуйте локальний порт на Deployment, потім відкрийте http://localhost:8080:

Термінал
kubectl --context dev port-forward deployment/hello 8080:80
    Зупинення й видалення кластера
Термінал
container cluster delete --name dev

Якщо вузол керування зупинився, наприклад після container system stop, видаліть кластер і створіть його знову. Тимчасовий кластер створюйте з --rm: його вузли видаляться, коли зупиняться.

    Поширені проблеми
  • cluster service unavailable: CLI інстальовано з Homebrew або служби не запущено. Інсталюйте підписаний пакет або перезапустіть служби командами container system stop і container system start. Gantry дає ту саму пораду в розділі «Кластери».
  • Старого кластера немає в списку: CLI 1.7 не показує кластери, створені в 1.6 або раніше. Видаліть такий кластер командою container cluster delete --name <name>.
  • Вузли лишаються NotReady: ви використали --cni NONE. Застосуйте маніфест CNI.
  • Контейнер вузла не зупиняється: так задумано. container stop і delete відмовляються працювати з вузлами кластера; використовуйте container cluster delete.
    Порівняння з Docker Desktop і OrbStack

У Docker Desktop є вбудований Kubernetes на kubeadm (один вузол) або kind (кілька вузлів), а в OrbStack — вбудований кластер з одного вузла. container cluster запускає kubeadm на образах kindest/node, кожен вузол у власній ВМ, з кластерами з кількох вузлів і спільним сховищем образів. Див. повне порівняння.

Більше про apple/container

Покроковий посібник із роботою в терміналі — Kubernetes на Mac з Apple container. У посібнику з apple/container описано кожну команду container і відповідну функцію Gantry. Там само можна дізнатися, чим Gantry відрізняється від Docker Desktop, OrbStack і Podman Desktop.

Запитання й відповіді

Чи підтримує Apple container Kubernetes?

Так. CLI container створює кластери Kubernetes, вузли яких працюють як контейнери: container cluster у CLI 1.6.1 і 1.7, container k8s у CLI від 1.5.0 до 1.6.0. Gantry дає для цього GUI.

Чи підтримує Gantry container cluster?

Так. Gantry показує, створює й видаляє кластери на хостах apple/container, показує їхні вузли, записує kubeconfig і відкриває кластер у своєму браузері Kubernetes. У CLI 1.7 він також задає розмір робочих вузлів і вмикає спільне сховище образів. Він використовує cluster або k8s залежно від версії CLI.

Як під’єднати kubectl до кластера apple/container?

Під час створення кластера CLI додає в ~/.kube/config контекст kubeconfig із назвою кластера. Виконайте kubectl --context <name> get nodes. Щоб мати окремий файл kubeconfig, натисніть Записати kubeconfig у Gantry; типовий шлях — ~/.kube/<name>.kubeconfig.

Як імпортувати локальний образ у кластер без реєстру?

У CLI 1.7 створіть кластер із параметром Використовувати локальні образи (--shared-image-store). Тоді поди запускають за назвою образи, які ви зібрали чи отримали за допомогою container. У CLI 1.5 і 1.6 клацніть образ у розділі «Образи» правою кнопкою й виберіть Імпортувати в кластер; Gantry виконає container cluster load-image. У CLI 1.7 команди load-image більше немає.

Чи можна створити кластер із кількох вузлів?

Так. Укажіть кількість робочих вузлів у вікні створення; для робочих вузлів потрібен CLI 1.6.0 або новіший. У CLI 1.7 ви також задаєте CPU і пам’ять робочих вузлів окремо від вузла керування.

Чи можна використати власний CNI, наприклад Calico або Cilium?

Так. Виберіть Власний маніфест і вкажіть файл маніфесту або виберіть Немає й інсталюйте CNI самостійно після запуску кластера. Поки CNI не працює, вузли лишаються в стані NotReady. Для Немає потрібен CLI 1.6.0 або новіший. Типовий CNI — вбудований маніфест kindnet.

Чому Gantry повідомляє, що служби кластера недоступні?

Служби container не відповіли на команду кластера. Якщо ваш CLI — збірка Homebrew без служб кластера, Gantry повідомляє про це й дає посилання на підписаний інсталятор на сторінці релізів apple/container. В інших випадках він пропонує Перезапустити служби.

Чи потрібен kubectl, щоб працювати з кластером у Gantry?

Поки що так: браузер Kubernetes у Gantry запускає kubectl. Якщо його не інстальовано, браузер показує команду brew install kubectl і може виконати її за вас.

Чи можна запустити Kubernetes на Mac без Docker?

Так. CLI container від Apple сам створює кластери Kubernetes командою container cluster create. Кожен вузол працює як легка ВМ, і вам не потрібні Docker, Docker Desktop, kind чи minikube.

Скільки вузлів може мати container cluster?

Один вузол керування й стільки робочих вузлів, скільки дозволяють CPU і пам’ять вашого Mac. Задайте їх прапорцем --workers; у CLI 1.7 кожна група робочих вузлів може мати власні CPU і пам’ять.

Яку версію Kubernetes використовує container cluster?

CLI 1.7.1 типово використовує образ вузла kindest/node:v1.35.5. Іншу версію виберіть прапорцем --node-image, наприклад docker.io/kindest/node:v1.34.11. Gantry показує версію в огляді кластера.
