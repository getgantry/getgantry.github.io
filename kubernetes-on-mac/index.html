Gantry/Kubernetes on a Mac

Run Kubernetes on a Mac with Apple container

Apple's container tool can create a local Kubernetes cluster in one command. Each node is a lightweight virtual machine on your Mac. This guide goes from an empty Mac to a running deployment, first in the terminal and then in Gantry.

In short. Install the signed container 1.7.1 package, run container cluster create --name dev --cpus 2 --memory 2g --workers count=2,cpus=2,memory=2g --shared-image-store, build an image with container build and run it in the cluster by name. Gantry shows the same cluster in a window: nodes, pods, logs, a shell and port forwards.

What you need

  • A Mac with Apple silicon and macOS 26 or later.
  • The container CLI 1.7.1 from the signed .pkg on the apple/container releases page. The Homebrew build of 1.7.1 does not include the cluster services, so container cluster fails with cluster service unavailable.
  • About 6 GB of free memory for the example below: three nodes with 2 GB each.
  • kubectl if you want to use the cluster from the terminal (brew install kubectl).

Start the services once after you install the package:

Terminal
container system start

Create the cluster

This command makes a cluster named dev with one control-plane node and two workers. Each node gets 2 CPUs and 2 GB of memory:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M sizes a group of workers. Repeat it for groups of different sizes. Without --workers, one node is both control plane and worker.
  • --cpus and --memory size the control plane. The default is a quarter of the CPUs and memory of your Mac, at least 2 CPUs and 2 GB.
  • --shared-image-store lets the nodes use your local images (see below). You cannot change it later: delete the cluster and create it again.
  • --cni ./calico.yaml installs your own CNI instead of the bundled kindnet; --cni NONE installs none.

The CLI adds a context named dev to ~/.kube/config. Check the nodes:

Terminal
container cluster list --nodes
kubectl --context dev get nodes

Run a local image without a registry

With --shared-image-store, the nodes can run any image in your local container image store. Build an image and use it by name:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Note
After you rebuild the same tag, run kubectl rollout restart with imagePullPolicy: Always, or use a new tag. With IfNotPresent, a node keeps the copy it already has. Anything with root on a node can read every image in your local store, including private images, so use the shared store for local development only.

On CLI 1.5 and 1.6 there is no shared store. Use container cluster load-image there, or Load into Cluster in Gantry. CLI 1.7 removed load-image.

Open the app in a browser

Forward a local port to the deployment, then open http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80

Browse the cluster in Gantry

Gantry shows the same cluster without commands. Add your apple/container host, open Clusters, and select dev. The overview shows the Kubernetes version, the image store, the workers and their CPUs and memory. Click Browse Resources to open the Kubernetes section on that context.

  • Pods, deployments, stateful sets, daemon sets, services, ingresses, config maps, secrets, nodes and events, for one namespace or all of them.
  • Pod logs with follow and tail, a shell in the pod, and port forwards with a list that you can stop.
  • Scale, rollout restart, delete, and Apply YAML from a pasted manifest or a file.
  • Secret values stay masked until you click Reveal.

The Kubernetes browser runs kubectl. If it is missing, Gantry shows brew install kubectl and can run it for you. A native client that needs no kubectl is in development.

You can also create the cluster in Gantry: Clusters ▸ New Cluster has steppers for the control plane and the workers and a Use local images switch. More on the Kubernetes on apple/container page.

Stop and delete the cluster

Terminal
container cluster delete --name dev

If the control-plane node stops, for example after container system stop, delete the cluster and create it again. Create a throw-away cluster with --rm to remove its nodes when they stop.

Common problems

  • cluster service unavailable: the CLI is the Homebrew build, or the services are not running. Install the signed package, or restart the services with container system stop and container system start. Gantry shows the same advice in Clusters.
  • An old cluster is missing from the list: CLI 1.7 does not list clusters created with 1.6 or earlier. Remove one with container cluster delete --name <name>.
  • Nodes stay NotReady: you used --cni NONE. Apply a CNI manifest.
  • You cannot stop a node container: this is on purpose. container stop and delete refuse cluster nodes; use container cluster delete.

How this compares with Docker Desktop and OrbStack

Docker Desktop has built-in Kubernetes with kubeadm (one node) or kind (several nodes), and OrbStack has a built-in single-node cluster. container cluster runs kubeadm on kindest/node images, each node in its own VM, with multi-node clusters and the shared image store. See the full comparison.

Questions and answers

Can I run Kubernetes on a Mac without Docker?

Yes. Apple's container CLI creates Kubernetes clusters itself with container cluster create. Each node runs as a lightweight VM, and you do not need Docker, Docker Desktop, kind or minikube.

How many nodes can a container cluster have?

One control plane and as many workers as your Mac has CPUs and memory for. Set them with --workers; on CLI 1.7 each group of workers can have its own CPUs and memory.

How do I use a locally built image in the cluster?

Create the cluster with --shared-image-store (CLI 1.7), build the image with container build -t name:tag . and use name:tag in the pod spec. No registry is needed.

Which Kubernetes version does container cluster use?

CLI 1.7.1 uses the kindest/node:v1.35.5 node image by default. Choose another version with --node-image, for example docker.io/kindest/node:v1.34.11. Gantry shows the version in the cluster overview.

Is there a GUI for container cluster?

Yes. Gantry creates and deletes clusters, shows the nodes, and browses pods, deployments, services, logs and secrets in its Kubernetes section. It is free and open source.
