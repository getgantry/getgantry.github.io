Gantry/Kubernetes no apple/container

Kubernetes no Apple container

O apple/container consegue executar um cluster Kubernetes cujos nós são contentores no seu Mac. O Gantry é uma GUI para isso: crie um cluster, veja os nós a arrancar, execute nele as suas imagens locais e explore os pods, os logs e os serviços, sem longas linhas de comando container cluster.

Em resumo. Num host apple/container, a secção Clusters do Gantry cria e elimina clusters Kubernetes com container cluster (CLI 1.6.1 e 1.7) ou container k8s (CLI 1.5.0 a 1.6.0). Na CLI 1.7.1, define o tamanho dos workers separadamente do plano de controlo e ativa o armazenamento de imagens partilhado. A secção Kubernetes explora o cluster: pods, logs, shell, reencaminhamento de portas, escalar e Aplicar YAML.

Requisitos

  • Um Mac com Apple silicon, macOS 26 e o Gantry (brew install --cask getgantry/tap/gantry).
  • A CLI container 1.5.0 ou posterior; recomenda-se a 1.7.1. Os workers e a CNI Nenhum requerem a 1.6.0 ou posterior. Os tamanhos dos workers e o armazenamento de imagens partilhado requerem a 1.7.0 ou posterior. Utilize o pacote de instalação assinado: a compilação do Homebrew da 1.7.1 não tem os serviços do cluster.
  • O kubectl para o explorador Kubernetes e para o terminal. O Gantry pode instalá-lo com o Homebrew.

Criar um cluster

  1. Selecione o seu host apple/container e abra Clusters na barra lateral.
  2. Inicie um novo cluster e preencha as opções abaixo.
  3. Crie-o. A lista mostra o novo cluster com o progresso em direto. Cancelar interrompe a criação e elimina os nós já criados.
OpçãoFlag da CLINotas
Nome--nameÉ também o nome do contexto do kubeconfig
Workers--workersNúmero de nós worker. CLI 1.6.0+
CPU e memória dos workers--workers count=N,cpus=C,memory=MCLI 1.7+. Antes da 1.7, --cpus e --memory definem todos os nós
CPU--cpusPlano de controlo (CLI 1.7+) ou todos os nós (antes da 1.7)
Memória--memoryPlano de controlo (CLI 1.7+) ou todos os nós (antes da 1.7), por exemplo 4G
Utilizar imagens locais--shared-image-storeCLI 1.7+. Os nós executam imagens do seu armazenamento de imagens local
Imagem dos nós--node-imageVazio mantém a predefinição da CLI
CNI--cniPredefinição (kindnet incluído), Nenhum (NONE, CLI 1.6.0+) ou o caminho de um manifesto personalizado

O mesmo comando na CLI:

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Nós e detalhes do cluster

A lista de clusters mostra uma linha para cada cluster. A vista de detalhe tem uma Vista geral (contexto kubectl, servidor da API, versão do Kubernetes, armazenamento de imagens, workers e respetivos recursos, rede dos nós), uma tabela de Nós e Inspecionar para os dados em bruto dos nós. A barra de ferramentas tem Explorar recursos, e o menu Mais tem Escrever kubeconfig, Copiar comando de contexto kubectl e Eliminar.

Os nós do cluster são contentores, mas pertencem ao container cluster. O Gantry desativa iniciar, parar, reiniciar, remover e mudar o nome de um nó e explica porquê, e as ações Iniciar todos e Parar todos ignoram os nós. Na CLI 1.7, a CLI também oculta os nós em container list. Os clusters criados com a CLI 1.6 ou anterior não aparecem na lista da 1.7; remova-os com container cluster delete --name <name>.

Explorar o cluster

Clique em Explorar recursos num cluster em execução ou abra Kubernetes na barra lateral. A secção não precisa de host e lista todos os contextos do kubeconfig; os contextos dos clusters do apple/container aparecem primeiro. Escolha um espaço de nomes ou todos os espaços de nomes e, em seguida, um tipo: pods, Deployments, StatefulSets, DaemonSets, serviços, Ingress, ConfigMaps, segredos, nós ou eventos.

  • Pods: logs com acompanhamento, últimas linhas e o contentor anterior; uma shell no pod; reencaminhamento de porta para 127.0.0.1.
  • Cargas de trabalho: escalar Deployments e StatefulSets; reiniciar um rollout.
  • Segredos: os valores ficam ocultos na lista e no YAML até clicar em Mostrar.
  • Aplicar YAML: cole um manifesto ou abra um ficheiro; os erros aparecem na folha.

O explorador executa o kubectl. Se o Gantry não o encontrar, a secção mostra brew install kubectl com um botão que o executa. Está em desenvolvimento um cliente Kubernetes nativo que não precisa do kubectl.

Ligar o kubectl

Ao criar o cluster, a CLI adiciona a ~/.kube/config um contexto com o nome do cluster. Use Copiar comando de contexto kubectl no Gantry, ou escreva-o:

Shell
kubectl --context dev get nodes

Para manter o cluster num ficheiro próprio, use Escrever kubeconfig. O Gantry executa container cluster write-config; o caminho predefinido é ~/.kube/<name>.kubeconfig.

Utilizar imagens locais no cluster

Na CLI 1.7, ative Utilizar imagens locais ao criar o cluster. Isto acrescenta --shared-image-store, para que os nós possam executar, pelo nome e sem registo, qualquer imagem que compilar ou descarregar com o container. A definição fica fixa na criação. Depois de recompilar uma tag, use imagePullPolicy: Always ou uma nova tag. Os pods privilegiados podem ler todas as imagens do seu armazenamento local, por isso reserve esta opção para desenvolvimento local.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

Nas CLI 1.5 e 1.6, clique com o botão direito na imagem em Imagens e escolha Carregar no cluster. O Gantry executa container cluster load-image, que copia a imagem para o containerd de cada nó. A CLI 1.7 removeu este comando, por isso o Gantry oculta aí a ação.

Shell
container cluster load-image --name dev myapp:dev

Quando os serviços do cluster não respondem

Se um comando de cluster falhar com cluster service unavailable, o Gantry verifica como a CLI está instalada. Uma compilação do Homebrew sem os plug-ins do cluster recebe a mensagem de que lhe faltam os serviços do cluster e uma ligação Descarregar instalador… para o pacote assinado. Nos outros casos, o Gantry oferece Reiniciar serviços….

Escolher uma CNI

A predefinição é o manifesto kindnet incluído. Escolha Manifesto personalizado para instalar a sua própria CNI a partir de um ficheiro, por exemplo Calico ou Cilium. Escolha Nenhum para instalar uma CNI manualmente mais tarde; até lá, os nós ficam NotReady.

Clusters a partir de agentes de IA

O servidor MCP do Gantry tem list_clusters, create_cluster e delete_cluster, por isso um agente como o Claude Code pode criar um cluster temporário para um teste e removê-lo no fim.

Adicionar o servidor MCP do Gantry
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Perguntas e respostas

O Apple container suporta Kubernetes?

Sim. A CLI container cria clusters Kubernetes cujos nós são executados como contentores: container cluster nas CLI 1.6.1 e 1.7, container k8s nas CLI 1.5.0 a 1.6.0. O Gantry dá-lhe uma GUI.

O Gantry suporta o container cluster?

Sim. O Gantry lista, cria e elimina clusters em hosts apple/container, mostra os respetivos nós, escreve o kubeconfig e abre o cluster no seu explorador Kubernetes. Na CLI 1.7, também define o tamanho dos workers e ativa o armazenamento de imagens partilhado. Usa cluster ou k8s de acordo com a sua versão da CLI.

Como usar o kubectl com um cluster do apple/container?

Quando a CLI cria um cluster, adiciona a ~/.kube/config um contexto kubeconfig com o nome do cluster. Execute kubectl --context <name> get nodes. Para manter um ficheiro separado, use Escrever kubeconfig no Gantry; o caminho predefinido é ~/.kube/<name>.kubeconfig.

Como colocar uma imagem local no cluster sem um registo?

Na CLI 1.7, crie o cluster com Utilizar imagens locais (--shared-image-store). Os pods executam então, pelo nome, as imagens que compilar ou descarregar com o container. Nas CLI 1.5 e 1.6, clique com o botão direito na imagem em Imagens e escolha Carregar no cluster; o Gantry executa container cluster load-image. A CLI 1.7 removeu o load-image.

É possível criar um cluster com vários nós?

Sim. Defina o número de workers na folha de criação; os workers requerem a CLI 1.6.0 ou posterior. Na CLI 1.7, também define as CPU e a memória dos workers separadamente do plano de controlo.

Posso usar a minha própria CNI, como Calico ou Cilium?

Sim. Escolha Manifesto personalizado e selecione o ficheiro do manifesto, ou escolha Nenhum e aplique uma CNI manualmente depois de o cluster arrancar. Os nós ficam NotReady até haver uma CNI em execução. Nenhum requer a CLI 1.6.0 ou posterior. A CNI predefinida é o manifesto kindnet incluído.

Porque é que o Gantry diz que os serviços do cluster estão indisponíveis?

Os serviços do container não responderam a um comando de cluster. Se a sua CLI for uma compilação do Homebrew sem os serviços do cluster, o Gantry indica-o e apresenta uma ligação para o instalador assinado na página de versões do apple/container. Caso contrário, oferece Reiniciar serviços.

Preciso do kubectl para usar o cluster no Gantry?

Por agora, sim: o explorador Kubernetes do Gantry executa o kubectl. Se não estiver instalado, o explorador mostra o comando brew install kubectl e pode executá-lo por si. Está em desenvolvimento um cliente Kubernetes nativo que elimina este passo.
