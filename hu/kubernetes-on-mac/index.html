Gantry/Kubernetes Macen

Kubernetes futtatása Macen az Apple containerrel

Az Apple container eszköze egyetlen paranccsal létrehoz egy helyi Kubernetes-klasztert. Minden csomópont egy könnyű virtuális gép a Macen. Ez az útmutató az üres Mactől egy futó deploymentig vezet, először a terminálban, majd a Gantryben.

Röviden. Telepítse az aláírt container 1.7.1-csomagot, futtassa a container cluster create --name dev --cpus 2 --memory 2g --workers count=2,cpus=2,memory=2g --shared-image-store parancsot, buildeljen egy image-et a container build paranccsal, és futtassa név szerint a klaszterben. A Gantry ugyanezt a klasztert egy ablakban mutatja: csomópontok, podok, naplók, shell és porttovábbítás.

Amire szükség van

  • Apple chipes Mac macOS 26-tal vagy újabbal.
  • A container CLI 1.7.1 az aláírt .pkg csomagból, az apple/container kiadási oldaláról. Az 1.7.1 Homebrew-buildje nem tartalmazza a klaszterszolgáltatásokat, ezért a container cluster a cluster service unavailable hibával leáll.
  • Az alábbi példához körülbelül 6 GB szabad memória: három csomópont, egyenként 2 GB.
  • kubectl, ha a terminálból szeretné használni a klasztert (brew install kubectl).

A csomag telepítése után egyszer indítsa el a szolgáltatásokat:

Terminál
container system start

A klaszter létrehozása

Ez a parancs dev nevű klasztert hoz létre egy vezérlősík-csomóponttal és két workerrel. Minden csomópont 2 CPU-t és 2 GB memóriát kap:

Terminál
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • A --workers count=N,cpus=C,memory=M workerek egy csoportját méretezi. Eltérő méretű csoportokhoz ismételje meg. --workers nélkül egyetlen csomópont a vezérlősík és a worker is.
  • A --cpus és a --memory a vezérlősíkot méretezi. Az alapérték a Mac CPU-inak és memóriájának negyede, legalább 2 CPU és 2 GB.
  • A --shared-image-store lehetővé teszi, hogy a csomópontok a helyi image-eket használják (lásd lent). Később nem módosítható: törölje a klasztert, és hozza létre újra.
  • A --cni ./calico.yaml a beépített kindnet helyett saját CNI-t telepít; a --cni NONE nem telepít CNI-t.

A CLI egy dev nevű környezetet ad a ~/.kube/config fájlhoz. Ellenőrizze a csomópontokat:

Terminál
container cluster list --nodes
kubectl --context dev get nodes

Helyi image futtatása registry nélkül

A --shared-image-store kapcsolóval a csomópontok a helyi container image-tár bármely image-ét futtathatják. Buildeljen egy image-et, és használja név szerint:

Terminál
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Megjegyzés
Ha ugyanazt a címkét újrabuildeli, futtassa a kubectl rollout restart parancsot imagePullPolicy: Always beállítással, vagy használjon új címkét. IfNotPresent esetén a csomópont megtartja a már meglévő példányt. Bármi, ami root jogosultsággal fut egy csomóponton, a helyi tár összes image-ét olvashatja, a privát image-eket is, ezért a közös tárat csak helyi fejlesztéshez használja.

A CLI 1.5-ben és 1.6-ban nincs közös tár. Ott használja a container cluster load-image parancsot, vagy a Gantryben a Betöltés a klaszterbe parancsot. A CLI 1.7-ből kikerült a load-image.

Az alkalmazás megnyitása böngészőben

Továbbítson egy helyi portot a deploymenthez, majd nyissa meg a http://localhost:8080 címet:

Terminál
kubectl --context dev port-forward deployment/hello 8080:80

A klaszter böngészése a Gantryben

A Gantry parancsok nélkül mutatja meg ugyanezt a klasztert. Adja hozzá az apple/container-gazdagépet, nyissa meg a Klaszterek szakaszt, és jelölje ki a dev klasztert. Az áttekintés mutatja a Kubernetes-verziót, az image-tárat, a workereket, valamint azok CPU-it és memóriáját. Kattintson az Erőforrások böngészése gombra, hogy ezzel a környezettel megnyíljon a Kubernetes szakasz.

  • Podok, deploymentek, StatefulSetek, DaemonSetek, szolgáltatások, ingressek, ConfigMapek, Secretek, csomópontok és események, egy névtérben vagy az összesben.
  • Podnaplók követéssel és a végük megjelenítésével, shell a podban, valamint porttovábbítás egy listával, amelyből leállíthatja őket.
  • Skálázás, rollout-újraindítás, törlés és YAML alkalmazása beillesztett manifestből vagy fájlból.
  • A Secretek értékei rejtve maradnak, amíg a Megjelenítés gombra nem kattint.

A Kubernetes-böngésző a kubectl eszközt futtatja. Ha hiányzik, a Gantry megmutatja a brew install kubectl parancsot, és le is tudja futtatni. Fejlesztés alatt áll egy natív kliens, amelyhez nem kell kubectl.

A klasztert a Gantryben is létrehozhatja: a Klaszterek ▸ Új klaszter lapon léptetők vannak a vezérlősíkhoz és a workerekhez, valamint egy Helyi image-ek használata kapcsoló. Bővebben a Kubernetes az apple/containeren oldalon.

A klaszter leállítása és törlése

Terminál
container cluster delete --name dev

Ha a vezérlősík-csomópont leáll, például a container system stop után, törölje a klasztert, és hozza létre újra. Ideiglenes klasztert a --rm kapcsolóval hozhat létre: ekkor a csomópontjai leálláskor törlődnek.

Gyakori problémák

  • cluster service unavailable: a CLI Homebrew-build, vagy a szolgáltatások nem futnak. Telepítse az aláírt csomagot, vagy indítsa újra a szolgáltatásokat a container system stop és a container system start paranccsal. A Gantry ugyanezt a tanácsot adja a Klaszterek szakaszban.
  • Egy régi klaszter hiányzik a listából: a CLI 1.7 nem listázza az 1.6-tal vagy korábbival létrehozott klasztereket. Ezeket a container cluster delete --name <name> paranccsal távolíthatja el.
  • A csomópontok NotReady állapotban maradnak: a --cni NONE kapcsolót használta. Alkalmazzon egy CNI-manifestet.
  • Egy csomópont-konténer nem állítható le: ez szándékos. A container stop és a delete elutasítja a klaszter csomópontjait; használja a container cluster delete parancsot.

Összevetés a Docker Desktoppal és az OrbStackkel

A Docker Desktopban beépített Kubernetes van kubeadm-mel (egy csomópont) vagy kinddal (több csomópont), az OrbStackben pedig beépített egycsomópontos klaszter. A container cluster kubeadm-et futtat kindest/node image-eken, minden csomópontot saját VM-ben, több csomópontos klaszterekkel és közös image-tárral. Lásd a teljes összevetést.

Kapcsolódó útmutatók

  • Átállás a Docker Desktopról az Apple containerre: parancsok, Compose, kötetek és hiányok
  • Konténerek és kötetek tárolása külső meghajtón Macen
  • Konténer létrehozása docker run parancsból Macen (docker run → container run)
  • Apple container GUI Macre: a teljes apple/container-útmutató
  • Kubernetes az Apple containeren: GUI a container clusterhez és Kubernetes-böngésző

Kérdések és válaszok

Futtatható Kubernetes Macen Docker nélkül?

Igen. Az Apple container CLI-je maga hoz létre Kubernetes-klasztereket a container cluster create paranccsal. Minden csomópont könnyű VM-ként fut, és nincs szükség Dockerre, Docker Desktopra, kindra vagy minikube-ra.

Hány csomópontja lehet egy container clusternek?

Egy vezérlősík és annyi worker, amennyihez a Macen elég CPU és memória van. Ezeket a --workers kapcsolóval adhatja meg; a CLI 1.7-ben a workerek minden csoportja saját CPU- és memóriabeállítást kaphat.

Hogyan használható egy helyben buildelt image a klaszterben?

Hozza létre a klasztert a --shared-image-store kapcsolóval (CLI 1.7), buildelje az image-et a container build -t name:tag . paranccsal, és használja a name:tag nevet a pod specifikációjában. Nincs szükség registryre.

Melyik Kubernetes-verziót használja a container cluster?

A CLI 1.7.1 alapértelmezés szerint a kindest/node:v1.35.5 csomópont-image-et használja. Más verziót a --node-image kapcsolóval választhat, például docker.io/kindest/node:v1.34.11. A Gantry a klaszter-áttekintésben mutatja a verziót.

Van GUI a container clusterhez?

Igen. A Gantry létrehozza és törli a klasztereket, megmutatja a csomópontokat, és a Kubernetes szakaszában böngészi a podokat, a deploymenteket, a szolgáltatásokat, a naplókat és a Secreteket. Ingyenes és nyílt forráskódú.
