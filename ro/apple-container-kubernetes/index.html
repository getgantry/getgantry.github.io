Gantry/Kubernetes pe apple/container

Kubernetes pe Apple container

apple/container poate rula un cluster Kubernetes ale cărui noduri sunt containere pe Mac. Gantry este un GUI pentru el: creați un cluster, urmăriți cum pornesc nodurile, rulați imaginile locale în el și răsfoiți pod-urile, jurnalele și serviciile, fără linii de comandă lungi container cluster.

Pe scurt. Pe o gazdă apple/container, secțiunea Clustere din Gantry creează și șterge clustere Kubernetes cu container cluster (CLI 1.6.1 și 1.7) sau container k8s (CLI 1.5.0–1.6.0). Pe CLI 1.7.1 dimensionează workerii separat de planul de control și activează depozitul de imagini partajat. Secțiunea Kubernetes răsfoiește clusterul: pod-uri, jurnale, shell, redirecționări de porturi, scalare și Aplică YAML.

Cerințe

  • Un Mac cu Apple silicon, macOS 26 și Gantry (brew install --cask getgantry/tap/gantry).
  • CLI-ul container 1.5.0 sau o versiune ulterioară; se recomandă 1.7.1. Workerii și CNI-ul Niciunul necesită 1.6.0 sau o versiune ulterioară. Dimensiunile workerilor și depozitul de imagini partajat necesită 1.7.0 sau o versiune ulterioară. Folosiți pachetul de instalare semnat: versiunea Homebrew a 1.7.1 nu are serviciile clusterului.
  • Nimic altceva pentru browserul Kubernetes din Gantry. kubectl doar dacă doriți să folosiți clusterul și din terminal.

Crearea unui cluster

  1. Selectați gazda apple/container și deschideți Clustere în bara laterală.
  2. Începeți un cluster nou și completați opțiunile de mai jos.
  3. Creați-l. Lista afișează noul cluster cu progresul în timp real. Anulează oprește crearea și șterge nodurile deja create.
OpțiuneFlag CLINote
Nume--nameEste și numele contextului din kubeconfig
Workeri--workersNumărul de noduri worker. CLI 1.6.0+
CPU-uri și memorie pentru workeri--workers count=N,cpus=C,memory=MCLI 1.7+. Înainte de 1.7, --cpus și --memory se aplică fiecărui nod
CPU-uri--cpusPlanul de control (CLI 1.7+) sau fiecare nod (înainte de 1.7)
Memorie--memoryPlanul de control (CLI 1.7+) sau fiecare nod (înainte de 1.7), de exemplu 4G
Folosește imaginile locale--shared-image-storeCLI 1.7+. Nodurile rulează imagini din depozitul dvs. local de imagini
Imaginea nodurilor--node-imageGol păstrează valoarea implicită a CLI-ului
CNI--cniImplicit (kindnet inclus), Niciunul (NONE, CLI 1.6.0+) sau calea către un manifest personalizat

Aceeași comandă în CLI:

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Noduri și detaliile clusterului

Lista de clustere afișează un rând pentru fiecare cluster. Vizualizarea detaliată are o filă Prezentare generală (context kubectl, server API, versiune Kubernetes, depozit de imagini, workerii și resursele lor, rețeaua nodurilor), un tabel Noduri și Inspectează pentru datele brute ale nodurilor. Bara de instrumente are Răsfoiește resursele, iar meniul Mai mult are Salvează kubeconfig, Copiază comanda de context kubectl și Șterge.

Nodurile clusterului sunt containere, dar le gestionează container cluster. Gantry dezactivează pornirea, oprirea, repornirea, eliminarea și redenumirea unui nod și vă spune de ce, iar Pornește tot și Oprește tot omit nodurile. Pe CLI 1.7, CLI-ul ascunde și nodurile din container list. Clusterele create cu CLI 1.6 sau o versiune anterioară nu apar în lista din 1.7; eliminați-le cu container cluster delete --name <name>.

Răsfoiți clusterul

Faceți clic pe Răsfoiește resursele pe un cluster care rulează sau deschideți Kubernetes în bara laterală. Secțiunea nu necesită o gazdă și listează fiecare context kubeconfig; contextele clusterelor apple/container apar primele. Alegeți un spațiu de nume sau toate spațiile de nume, apoi un tip: pod-uri, deployment-uri, StatefulSet-uri, DaemonSet-uri, servicii, Ingress-uri, ConfigMap-uri, secrete, noduri sau evenimente.

  • Pod-uri: jurnale cu urmărire, ultimele linii și containerul anterior; un shell în pod; redirecționare de port către 127.0.0.1.
  • Sarcini de lucru: scalați deployment-uri și StatefulSet-uri; reporniți un rollout.
  • Secrete: valorile sunt mascate în listă și în YAML până când faceți clic pe Afișează.
  • Aplică YAML: lipiți un manifest sau deschideți un fișier; erorile apar în foaie.

Gantry comunică direct cu API-ul Kubernetes, cu datele de autentificare din kubeconfig. Nu aveți nevoie de kubectl sau de alt instrument: un cluster creat cu container cluster create poate fi răsfoit imediat.

Conectarea kubectl

Când creează clusterul, CLI-ul adaugă în ~/.kube/config un context cu numele clusterului. Folosiți Copiază comanda de context kubectl în Gantry sau tastați comanda:

Shell
kubectl --context dev get nodes

Pentru a păstra clusterul într-un fișier separat, folosiți Salvează kubeconfig. Gantry rulează container cluster write-config; calea implicită este ~/.kube/<name>.kubeconfig.

Folosiți imagini locale în cluster

Pe CLI 1.7, activați Folosește imaginile locale când creați clusterul. Opțiunea adaugă --shared-image-store, astfel încât nodurile pot rula, după nume, orice imagine pe care o construiți sau o descărcați cu container, fără registru. Setarea se fixează la creare. După ce reconstruiți un tag, folosiți imagePullPolicy: Always sau un tag nou. Pod-urile privilegiate pot citi orice imagine din depozitul dvs. local, deci folosiți această opțiune doar pentru dezvoltare locală.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

Pe CLI 1.5 și 1.6, faceți clic dreapta pe imagine în Imagini și alegeți Încarcă în cluster. Gantry rulează container cluster load-image, care copiază imaginea în containerd-ul fiecărui nod. CLI 1.7 a eliminat această comandă, așa că Gantry ascunde acolo acțiunea.

Shell
container cluster load-image --name dev myapp:dev

Când serviciile clusterului nu răspund

Dacă o comandă de cluster eșuează cu cluster service unavailable, Gantry verifică modul în care este instalat CLI-ul. O versiune Homebrew fără pluginurile de cluster primește mesajul că îi lipsesc serviciile clusterului și un link Descarcă programul de instalare… către pachetul semnat. În celelalte cazuri, Gantry oferă Repornește serviciile….

Alegerea unui CNI

Implicit se folosește manifestul kindnet inclus. Alegeți Manifest personalizat pentru a instala propriul CNI dintr-un fișier, de exemplu Calico sau Cilium. Alegeți Niciunul pentru a instala manual un CNI mai târziu; până atunci, nodurile rămân NotReady.

Rulați Kubernetes pe Mac cu Apple container

Instrumentul container de la Apple poate crea un cluster Kubernetes local cu o singură comandă. Fiecare nod este o mașină virtuală ușoară pe Mac. Acest ghid pornește de la un Mac gol și ajunge la un deployment care rulează, mai întâi în terminal, apoi în Gantry.

De ce aveți nevoie

  • Un Mac cu Apple silicon și macOS 26 sau o versiune ulterioară.
  • CLI-ul container 1.7.1 din pachetul semnat .pkg de pe pagina de versiuni apple/container. Versiunea Homebrew a 1.7.1 nu include serviciile clusterului, așa că container cluster eșuează cu cluster service unavailable.
  • Aproximativ 6 GB de memorie liberă pentru exemplul de mai jos: trei noduri cu câte 2 GB.
  • kubectl, dacă doriți să folosiți clusterul din terminal (brew install kubectl).

Porniți serviciile o dată, după ce instalați pachetul:

Terminal
container system start
    Creați clusterul

Această comandă creează un cluster numit dev cu un nod de plan de control și doi workeri. Fiecare nod primește 2 CPU-uri și 2 GB de memorie:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M dimensionează un grup de workeri. Repetați opțiunea pentru grupuri de dimensiuni diferite. Fără --workers, un singur nod este atât plan de control, cât și worker.
  • --cpus și --memory dimensionează planul de control. Valoarea implicită este un sfert din CPU-urile și memoria Mac-ului, cel puțin 2 CPU-uri și 2 GB.
  • --shared-image-store permite nodurilor să folosească imaginile dvs. locale (vedeți mai jos). Nu o puteți schimba ulterior: ștergeți clusterul și creați-l din nou.
  • --cni ./calico.yaml instalează propriul CNI în locul kindnet inclus; --cni NONE nu instalează niciunul.

CLI-ul adaugă în ~/.kube/config un context numit dev. Verificați nodurile:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Rulați o imagine locală fără registru

Cu --shared-image-store, nodurile pot rula orice imagine din depozitul local de imagini container. Construiți o imagine și folosiți-o după nume:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Notă
După ce reconstruiți același tag, rulați kubectl rollout restart cu imagePullPolicy: Always sau folosiți un tag nou. Cu IfNotPresent, un nod păstrează copia pe care o are deja. Orice rulează ca root pe un nod poate citi orice imagine din depozitul dvs. local, inclusiv imaginile private, deci folosiți depozitul partajat doar pentru dezvoltare locală.

Pe CLI 1.5 și 1.6 nu există depozit partajat. Acolo folosiți container cluster load-image sau Încarcă în cluster în Gantry. CLI 1.7 a eliminat load-image.

    Deschideți aplicația într-un browser

Redirecționați un port local către deployment, apoi deschideți http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Opriți și ștergeți clusterul
Terminal
container cluster delete --name dev

Dacă nodul de plan de control se oprește, de exemplu după container system stop, ștergeți clusterul și creați-l din nou. Creați un cluster temporar cu --rm, ca nodurile să fie eliminate când se opresc.

    Probleme frecvente
  • cluster service unavailable: CLI-ul este versiunea Homebrew sau serviciile nu rulează. Instalați pachetul semnat sau reporniți serviciile cu container system stop și container system start. Gantry afișează același sfat în Clustere.
  • Un cluster vechi lipsește din listă: CLI 1.7 nu listează clusterele create cu 1.6 sau cu o versiune anterioară. Eliminați unul cu container cluster delete --name <name>.
  • Nodurile rămân NotReady: ați folosit --cni NONE. Aplicați un manifest CNI.
  • Nu puteți opri containerul unui nod: este intenționat. container stop și delete refuză nodurile de cluster; folosiți container cluster delete.
    Comparație cu Docker Desktop și OrbStack

Docker Desktop are Kubernetes integrat cu kubeadm (un nod) sau kind (mai multe noduri), iar OrbStack are un cluster integrat cu un singur nod. container cluster rulează kubeadm pe imagini kindest/node, fiecare nod în propria VM, cu clustere cu mai multe noduri și depozitul de imagini partajat. Vedeți comparația completă.

Clustere din agenți AI

Serverul MCP Gantry are list_clusters, create_cluster și delete_cluster, așa că un agent precum Claude Code poate crea un cluster temporar pentru un test și îl poate elimina după aceea.

Adăugați serverul MCP Gantry
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Întrebări și răspunsuri

Apple container acceptă Kubernetes?

Da. CLI-ul container creează clustere Kubernetes ale căror noduri rulează ca containere: container cluster în CLI 1.6.1 și 1.7, container k8s în CLI 1.5.0–1.6.0. Gantry îi oferă un GUI.

Gantry acceptă container cluster?

Da. Gantry listează, creează și șterge clustere pe gazdele apple/container, afișează nodurile acestora, salvează kubeconfig și deschide clusterul în browserul său Kubernetes. Pe CLI 1.7 dimensionează și workerii și activează depozitul de imagini partajat. Folosește cluster sau k8s în funcție de versiunea CLI-ului dvs.

Cum folosesc kubectl cu un cluster apple/container?

Când CLI-ul creează un cluster, adaugă în ~/.kube/config un context kubeconfig cu numele clusterului. Rulați kubectl --context <name> get nodes. Pentru un fișier separat, folosiți Salvează kubeconfig în Gantry; calea implicită este ~/.kube/<name>.kubeconfig.

Cum pun o imagine locală în cluster fără registru?

Pe CLI 1.7, creați clusterul cu Folosește imaginile locale (--shared-image-store). Pod-urile rulează apoi, după nume, imaginile pe care le construiți sau le descărcați cu container. Pe CLI 1.5 și 1.6, faceți clic dreapta pe imagine în Imagini și alegeți Încarcă în cluster; Gantry rulează container cluster load-image. CLI 1.7 a eliminat load-image.

Pot crea un cluster cu mai multe noduri?

Da. Setați numărul de workeri în foaia de creare; workerii necesită CLI 1.6.0 sau o versiune ulterioară. Pe CLI 1.7 setați și CPU-urile și memoria workerilor separat de planul de control.

Pot folosi propriul CNI, de exemplu Calico sau Cilium?

Da. Alegeți Manifest personalizat și selectați fișierul manifest sau alegeți Niciunul și aplicați manual un CNI după ce clusterul pornește. Nodurile rămân NotReady până când rulează un CNI. Niciunul necesită CLI 1.6.0 sau o versiune ulterioară. CNI-ul implicit este manifestul kindnet inclus.

De ce spune Gantry că serviciile clusterului nu sunt disponibile?

Serviciile container nu au răspuns la o comandă de cluster. Dacă CLI-ul dvs. este o versiune Homebrew fără serviciile clusterului, Gantry vă spune acest lucru și oferă un link către programul de instalare semnat de pe pagina de versiuni apple/container. Altfel, oferă Repornește serviciile.

Am nevoie de kubectl pentru a folosi clusterul în Gantry?

Nu. Gantry comunică direct cu API-ul Kubernetes: citește kubeconfig, apoi listează resurse, transmite jurnale în timp real, deschide un shell, redirecționează porturi și aplică YAML fără kubectl. Un cluster creat cu container cluster create poate fi răsfoit imediat.

Pot rula Kubernetes pe Mac fără Docker?

Da. CLI-ul container de la Apple creează singur clustere Kubernetes cu container cluster create. Fiecare nod rulează ca o mașină virtuală ușoară și nu aveți nevoie de Docker, Docker Desktop, kind sau minikube.

Câte noduri poate avea un container cluster?

Un plan de control și atâția workeri câți permit CPU-urile și memoria Mac-ului. Setați-i cu --workers; pe CLI 1.7, fiecare grup de workeri poate avea propriile CPU-uri și memorie.

Ce versiune Kubernetes folosește container cluster?

CLI 1.7.1 folosește implicit imaginea de nod kindest/node:v1.35.5. Alegeți altă versiune cu --node-image, de exemplu docker.io/kindest/node:v1.34.11. Gantry afișează versiunea în prezentarea generală a clusterului.
