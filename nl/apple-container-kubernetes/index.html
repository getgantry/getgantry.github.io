Gantry/Kubernetes op apple/container

Kubernetes op Apple container

apple/container kan een Kubernetes-cluster draaien waarvan de nodes containers op je Mac zijn. Gantry is er een GUI voor: maak een cluster, zie de nodes opstarten, draai je lokale images erin en blader door de pods, logs en services, zonder lange container cluster-commandoregels.

Kort gezegd. Op een apple/container-host maakt en verwijdert het onderdeel Clusters van Gantry Kubernetes-clusters met container cluster (CLI 1.6.1 en 1.7) of container k8s (CLI 1.5.0 tot en met 1.6.0). Op CLI 1.7.1 stelt het de grootte van de workers apart van de control plane in en zet het de gedeelde imageopslag aan. Het onderdeel Kubernetes bladert door het cluster: pods, logs, shell, poortdoorsturingen, schalen en Pas YAML toe.

Vereisten

  • Een Mac met Apple silicon, macOS 26 en Gantry (brew install --cask getgantry/tap/gantry).
  • De container-CLI 1.5.0 of nieuwer; 1.7.1 wordt aanbevolen. Workers en de CNI Geen vereisen 1.6.0 of nieuwer. Workergroottes en de gedeelde imageopslag vereisen 1.7.0 of nieuwer. Gebruik het ondertekende installatiepakket: de Homebrew-build van 1.7.1 heeft geen clusterservices.
  • kubectl voor de Kubernetes-browser en de terminal. Gantry kan het met Homebrew installeren.

Een cluster maken

  1. Selecteer je apple/container-host en open Clusters in de navigatiekolom.
  2. Start een nieuw cluster en vul de opties hieronder in.
  3. Maak het aan. De lijst toont het nieuwe cluster met gestreamde voortgang. Annuleer stopt het aanmaken en verwijdert de nodes die al gemaakt waren.
OptieCLI-flagOpmerkingen
Naam--nameOok de naam van de kubeconfig-context
Workers--workersAantal workernodes. CLI 1.6.0+
CPU's en geheugen van workers--workers count=N,cpus=C,memory=MCLI 1.7+. Vóór 1.7 stellen --cpus en --memory elke node in
CPU's--cpusControl plane (CLI 1.7+), of elke node (vóór 1.7)
Geheugen--memoryControl plane (CLI 1.7+), of elke node (vóór 1.7), bijvoorbeeld 4G
Gebruik lokale images--shared-image-storeCLI 1.7+. Nodes draaien images uit je lokale imageopslag
Node-image--node-imageLeeg laten voor de standaard van de CLI
CNI--cniStandaard (meegeleverde kindnet), Geen (NONE, CLI 1.6.0+) of een pad naar een aangepast manifest

Hetzelfde commando in de CLI:

Shell
container cluster create --name dev --cpus 2 --memory 4G \
  --workers count=2,cpus=2,memory=4G --shared-image-store

Nodes en clusterdetails

De clusterlijst toont één rij per cluster. De detailweergave heeft een Overzicht (kubectl-context, API-server, Kubernetes-versie, imageopslag, workers en hun bronnen, nodenetwerk), een tabel Nodes en Inspecteren voor de ruwe nodegegevens. De knoppenbalk heeft Blader door resources, en het menu Meer heeft Schrijf Kubeconfig, Kopieer kubectl-contextcommando en Verwijder.

Clusternodes zijn containers, maar container cluster is de eigenaar. Gantry schakelt starten, stoppen, herstarten, verwijderen en hernoemen voor een node uit en vertelt je waarom, en Start alle en Stop alle slaan nodes over. Op CLI 1.7 verbergt de CLI nodes ook in container list. Clusters die met CLI 1.6 of ouder zijn gemaakt, staan niet in de lijst van 1.7; verwijder ze met container cluster delete --name <name>.

Door het cluster bladeren

Klik op Blader door resources bij een actief cluster, of open Kubernetes in de navigatiekolom. Het onderdeel heeft geen host nodig en toont elke kubeconfig-context; de contexten van apple/container-clusters staan bovenaan. Kies een namespace of alle namespaces, en dan een soort: pods, deployments, stateful sets, daemon sets, services, ingresses, config maps, secrets, nodes of gebeurtenissen.

  • Pods: logs met volgen, tail en de vorige container; een shell in de pod; poortdoorsturing naar 127.0.0.1.
  • Workloads: deployments en stateful sets schalen; een rollout herstarten.
  • Secrets: waarden zijn gemaskeerd in de lijst en in de YAML tot je op Toon klikt.
  • Pas YAML toe: plak een manifest of open een bestand; fouten verschijnen in het venster.

De browser voert kubectl uit. Vindt Gantry het niet, dan toont het onderdeel brew install kubectl met een knop die het uitvoert.

kubectl verbinden

De CLI voegt bij het aanmaken van het cluster een context met de naam van het cluster toe aan ~/.kube/config. Gebruik Kopieer kubectl-contextcommando in Gantry, of typ het zelf:

Shell
kubectl --context dev get nodes

Wil je het cluster in een eigen bestand, gebruik dan Schrijf Kubeconfig. Gantry voert container cluster write-config uit; het standaardpad is ~/.kube/<name>.kubeconfig.

Lokale images gebruiken in het cluster

Zet op CLI 1.7 Gebruik lokale images aan wanneer je het cluster maakt. Dat voegt --shared-image-store toe, zodat de nodes elke image die je met container bouwt of pullt op naam kunnen draaien, zonder registry. De instelling ligt vast bij het aanmaken. Gebruik na het opnieuw bouwen van een tag imagePullPolicy: Always of een nieuwe tag. Geprivilegieerde pods kunnen elke image in je lokale opslag lezen, dus gebruik dit alleen voor lokale ontwikkeling.

Shell
container build -t myapp:dev .
kubectl --context dev create deployment myapp --image=myapp:dev

Op CLI 1.5 en 1.6 klik je in Images met de rechtermuisknop op de image en kies je Laad in cluster. Gantry voert container cluster load-image uit, dat de image naar de containerd van elke node kopieert. CLI 1.7 heeft dit commando verwijderd, dus daar verbergt Gantry de actie.

Shell
container cluster load-image --name dev myapp:dev

Als de clusterservices niet antwoorden

Mislukt een clustercommando met cluster service unavailable, dan controleert Gantry hoe de CLI is geïnstalleerd. Bij een Homebrew-build zonder de clusterplug-ins krijg je de melding dat de build geen clusterservices heeft en een link Download installatieprogramma… naar het ondertekende pakket. In andere gevallen biedt Gantry Herstart services… aan.

Een CNI kiezen

De standaard is het meegeleverde kindnet-manifest. Kies Aangepast manifest om je eigen CNI, bijvoorbeeld Calico of Cilium, uit een bestand te installeren. Kies Geen om later zelf een CNI te installeren; tot die tijd blijven de nodes NotReady.

Kubernetes draaien op een Mac met Apple container

Apples container-tool kan met één commando een lokaal Kubernetes-cluster maken. Elke node is een lichte virtuele machine op je Mac. Deze gids gaat van een lege Mac naar een draaiende deployment, eerst in de terminal en daarna in Gantry.

Wat je nodig hebt

  • Een Mac met Apple silicon en macOS 26 of nieuwer.
  • De container-CLI 1.7.1 uit de ondertekende .pkg op de releasepagina van apple/container. De Homebrew-build van 1.7.1 bevat de clusterservices niet, dus container cluster mislukt met cluster service unavailable.
  • Ongeveer 6 GB vrij geheugen voor het voorbeeld hieronder: drie nodes met elk 2 GB.
  • kubectl als je het cluster vanuit de terminal wilt gebruiken (brew install kubectl).

Start de services één keer nadat je het pakket hebt geïnstalleerd:

Terminal
container system start
    Het cluster maken

Dit commando maakt een cluster met de naam dev met één control-plane-node en twee workers. Elke node krijgt 2 CPU's en 2 GB geheugen:

Terminal
container cluster create --name dev --cpus 2 --memory 2g \
  --workers count=2,cpus=2,memory=2g --shared-image-store
  • --workers count=N,cpus=C,memory=M stelt de grootte van een groep workers in. Herhaal het voor groepen van verschillende grootte. Zonder --workers is één node zowel control plane als worker.
  • --cpus en --memory stellen de grootte van de control plane in. De standaard is een kwart van de CPU's en het geheugen van je Mac, minstens 2 CPU's en 2 GB.
  • --shared-image-store laat de nodes je lokale images gebruiken (zie hieronder). Je kunt dit later niet wijzigen: verwijder het cluster en maak het opnieuw.
  • --cni ./calico.yaml installeert je eigen CNI in plaats van de meegeleverde kindnet; --cni NONE installeert er geen.

De CLI voegt een context met de naam dev toe aan ~/.kube/config. Controleer de nodes:

Terminal
container cluster list --nodes
kubectl --context dev get nodes
    Een lokale image draaien zonder registry

Met --shared-image-store kunnen de nodes elke image in je lokale container-imageopslag draaien. Bouw een image en gebruik die op naam:

Terminal
printf 'FROM nginx:alpine\n' > Dockerfile
container build -t hello:dev .
kubectl --context dev create deployment hello --image=hello:dev
kubectl --context dev get pods
Opmerking
Voer na het opnieuw bouwen van dezelfde tag kubectl rollout restart uit met imagePullPolicy: Always, of gebruik een nieuwe tag. Met IfNotPresent houdt een node de kopie die hij al heeft. Alles met root op een node kan elke image in je lokale opslag lezen, ook privé-images, dus gebruik de gedeelde opslag alleen voor lokale ontwikkeling.

Op CLI 1.5 en 1.6 is er geen gedeelde opslag. Gebruik daar container cluster load-image, of Laad in cluster in Gantry. CLI 1.7 heeft load-image verwijderd.

    De app openen in een browser

Stuur een lokale poort door naar de deployment en open dan http://localhost:8080:

Terminal
kubectl --context dev port-forward deployment/hello 8080:80
    Het cluster stoppen en verwijderen
Terminal
container cluster delete --name dev

Stopt de control-plane-node, bijvoorbeeld na container system stop, verwijder het cluster dan en maak het opnieuw. Maak een wegwerpcluster met --rm om de nodes te verwijderen zodra ze stoppen.

    Veelvoorkomende problemen
  • cluster service unavailable: de CLI is de Homebrew-build, of de services draaien niet. Installeer het ondertekende pakket, of herstart de services met container system stop en container system start. Gantry geeft hetzelfde advies in Clusters.
  • Een oud cluster ontbreekt in de lijst: CLI 1.7 toont geen clusters die met 1.6 of ouder zijn gemaakt. Verwijder zo'n cluster met container cluster delete --name <name>.
  • Nodes blijven NotReady: je hebt --cni NONE gebruikt. Pas een CNI-manifest toe.
  • Je kunt een nodecontainer niet stoppen: dat is zo bedoeld. container stop en delete weigeren clusternodes; gebruik container cluster delete.
    Vergeleken met Docker Desktop en OrbStack

Docker Desktop heeft ingebouwde Kubernetes met kubeadm (één node) of kind (meerdere nodes), en OrbStack heeft een ingebouwd cluster met één node. container cluster draait kubeadm op kindest/node-images, elke node in een eigen VM, met clusters van meerdere nodes en de gedeelde imageopslag. Zie de volledige vergelijking.

Clusters vanuit AI-agents

De Gantry MCP-server heeft list_clusters, create_cluster en delete_cluster, zodat een agent als Claude Code een tijdelijk cluster voor een test kan maken en het daarna weer kan verwijderen.

Voeg de Gantry MCP-server toe
claude mcp add gantry -- /Applications/Gantry.app/Contents/Resources/gantry-mcp

Meer over apple/container

Voor een stapsgewijze uitleg vanuit de terminal, lees Kubernetes draaien op een Mac met Apple container. Lees de apple/container-gids voor elk container-commando en de bijbehorende functie in Gantry, of bekijk hoe Gantry zich verhoudt tot Docker Desktop, OrbStack en Podman Desktop.

Vragen en antwoorden

Ondersteunt Apple container Kubernetes?

Ja. De container-CLI maakt Kubernetes-clusters waarvan de nodes als containers draaien: container cluster in CLI 1.6.1 en 1.7, container k8s in CLI 1.5.0 tot en met 1.6.0. Gantry voegt er een GUI aan toe.

Ondersteunt Gantry container cluster?

Ja. Gantry geeft een overzicht van clusters op apple/container-hosts, maakt en verwijdert ze, toont hun nodes, schrijft de kubeconfig en opent het cluster in de Kubernetes-browser. Op CLI 1.7 stelt het ook de grootte van de workers in en zet het de gedeelde imageopslag aan. Het gebruikt cluster of k8s, afhankelijk van je CLI-versie.

Hoe gebruik ik kubectl met een apple/container-cluster?

Wanneer de CLI een cluster maakt, voegt hij een kubeconfig-context met de naam van het cluster toe aan ~/.kube/config. Voer kubectl --context <name> get nodes uit. Wil je een apart bestand, gebruik dan Schrijf Kubeconfig in Gantry; het standaardpad is ~/.kube/<name>.kubeconfig.

Hoe krijg ik een lokale image in het cluster zonder registry?

Maak op CLI 1.7 het cluster met Gebruik lokale images (--shared-image-store). Pods draaien dan de images die je met container bouwt of pullt, op naam. Op CLI 1.5 en 1.6 klik je onder Images met de rechtermuisknop op de image en kies je Laad in cluster; Gantry voert container cluster load-image uit. CLI 1.7 heeft load-image verwijderd.

Kan ik een cluster met meerdere nodes maken?

Ja. Stel het aantal workers in bij het aanmaken; workers vereisen CLI 1.6.0 of nieuwer. Op CLI 1.7 stel je ook de CPU's en het geheugen van de workers in, los van de control plane.

Kan ik mijn eigen CNI gebruiken, zoals Calico of Cilium?

Ja. Kies Aangepast manifest en selecteer het manifestbestand, of kies Geen en installeer zelf een CNI nadat het cluster is gestart. Nodes blijven NotReady tot er een CNI draait. Geen vereist CLI 1.6.0 of nieuwer. De standaard-CNI is het meegeleverde kindnet-manifest.

Waarom meldt Gantry dat de clusterservices niet beschikbaar zijn?

De container-services hebben niet geantwoord op een clustercommando. Is je CLI een Homebrew-build zonder clusterservices, dan zegt Gantry dat en linkt het naar het ondertekende installatieprogramma op de releasepagina van apple/container. Anders biedt het Herstart services aan.

Heb ik kubectl nodig om het cluster in Gantry te gebruiken?

Voorlopig wel: de Kubernetes-browser van Gantry voert kubectl uit. Is dat niet geïnstalleerd, dan toont de browser het commando brew install kubectl en kan hij het voor je uitvoeren.

Kan ik Kubernetes draaien op een Mac zonder Docker?

Ja. Apples container-CLI maakt zelf Kubernetes-clusters met container cluster create. Elke node draait als lichte VM, en je hebt geen Docker, Docker Desktop, kind of minikube nodig.

Hoeveel nodes kan een container cluster hebben?

Eén control plane en zoveel workers als je Mac CPU's en geheugen heeft. Stel ze in met --workers; op CLI 1.7 kan elke groep workers eigen CPU's en geheugen hebben.

Welke Kubernetes-versie gebruikt container cluster?

CLI 1.7.1 gebruikt standaard de node-image kindest/node:v1.35.5. Kies een andere versie met --node-image, bijvoorbeeld docker.io/kindest/node:v1.34.11. Gantry toont de versie in het clusteroverzicht.
